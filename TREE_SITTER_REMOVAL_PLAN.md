# Tree-sitter Removal Plan

**Verdict: keep.** No phases below -- recorded in
[DEPENDENCIES.md](DEPENDENCIES.md)'s inventory for completeness, not
because removal is planned.

## What it's used for

`src/treesitter.cpp` uses tree-sitter's incremental-parsing runtime
(`third_party/tree-sitter`, vendored source, not fetched at configure
time -- see that directory's own README for why) plus a curated set of
compiled-in grammars (C, C++, Lua, Python, JavaScript, Markdown +
Markdown-inline, Org, R) for syntax highlighting, and every other
grammar via `LoadDynamicLanguage`/`TS_DYNAMIC_LANGUAGES` -- `dlopen`ing a
compiled `.so` the user already has (a Nix devShell's
`tree-sitter.withPlugins`, the tree-sitter CLI's build cache, an
nvim-treesitter install, or `~/.config/mep/parsers/`). This is already
the *minimal* footprint tree-sitter allows: 8 grammars compiled in,
everything else loaded dynamically at runtime, not linked.

## Why not

Tree-sitter itself (the C runtime `treesitter.cpp` calls into) is a
real incremental-parsing engine: a GLR-style parser core, an edit/
re-parse algorithm that reuses unchanged subtrees across keystrokes, and
per-grammar parser tables generated by tree-sitter's own grammar
compiler from each language's `grammar.js`. Reimplementing this in-house
would mean either:

- **Rewriting the runtime** (the edit-reuse algorithm, the parse table
  interpreter) -- a serious parsing-theory undertaking on its own, before
  a single grammar works.
- **Also rewriting the grammar compiler**, or hand-writing a parser per
  language -- the 8 compiled-in grammars alone (C, C++, Lua, Python,
  JavaScript, two Markdown variants, Org, R) each encode real language
  grammars (C++'s especially) that took their upstream maintainers
  significant effort to get right, and every dynamically-loaded grammar
  beyond those 8 would need the same treatment to keep working.

Unlike raylib -- where mep's own code (26k lines of `main.cpp`) already
*was* the rendering layer, just not abstracted -- mep's code here is a
thin consumer (`treesitter.cpp`) of a genuinely hard, general-purpose
parsing problem that's out of scope to own. The value tree-sitter
provides (broad language coverage via the dynamic-loading path, without
mep vendoring or maintaining parsers for languages it doesn't compile
in) would be lost entirely by going in-house for even the 8 built-in
grammars, let alone the open-ended dynamic set.

## If this ever gets revisited

If the dynamic-loading path (`dlopen`) ever became a liability (e.g. a
sandboxed/wasm-only target that can't `dlopen` at all -- already true,
and already handled by simply not offering that path under Emscripten),
the fallback is narrowing the compiled-in set further, not replacing the
engine.
