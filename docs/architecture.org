#+TITLE: How mep is put together

A map of the source tree, for anyone changing it. mep has no UI toolkit,
no browser engine, no PDF library and no game engine underneath it: the
window, the renderer, the font rasterizer, the document parsers and the
terminal emulator are all in =src/=. The only third-party code is Lua,
Tree-sitter (with its grammars) and a handful of small vendored parsers
under =third_party/=.

* The graphics layer

=src/gfx/= is the whole platform/rendering layer, behind one backend
interface (=backend.h=). There is no raylib, GLFW or SDL in the build.

| Area | Files |
|------+-------|
| Window, input, GL context | =backend_native.cpp= (X11 + GLX), =backend_native_emscripten_glfw.cpp= (WebGL2 via Emscripten) |
| 2D and 3D renderers | =backend_native_renderer2d.cpp=, =backend_native_renderer3d.cpp=, =gl_shader.cpp=, =gl_loader.cpp= |
| Text | =backend_native_text.cpp=, =truetype.cpp=, =cff.cpp=, =type1.cpp=, =rasterizer.cpp= |
| Model loading | =backend_native_model_{gltf,obj,iqm,m3d,vox}.cpp= |
| Audio | =backend_native_audio.cpp= (ALSA) |
| Math | =vecmath.h= (no backend dependency at all) |

The embedded font is JetBrains Mono Regular, compiled into the binary as
=src/font_data.h= so both builds start with a real font and no asset
fetch or preload step (license:
=third_party_licenses/JetBrainsMono-OFL.txt=).

* The editor core

- =src/editor.h= / =src/editor.cpp= — modes, motions, operators,
  per-buffer undo, buffers, panes, tabs, workspaces and projects
  (including per-project session save/restore), the =:= command line,
  and the Lua-facing API surface. Deliberately kept free of any
  rendering dependency.
- =src/main.cpp= — window init, the frame loop, and all drawing: it
  recursively renders the active workspace's tab's split-pane tree, the
  =[project] [workspace]= tab bar, every sidebar and every document
  mode's own pane. It also holds mep's built-in configuration, which is
  Lua source embedded as =kBuiltin*= string literals (the file tree, git
  panel, LSP client, org tooling, learning games and the rest are all
  written in that Lua, not in C++).
- =src/lua_env.h= / =src/lua_env.cpp= — the embedded Lua 5.4 state and
  the =mep.*= C bindings. See [[file:lua-api.org][the Lua API]].
- =src/workspace_git.h= / =src/workspace_git.cpp= — pure helpers behind
  git-worktree-backed workspaces (worktree dir derivation, =git worktree
  list --porcelain= parsing, name validation, session-file paths);
  unit-tested by =mep-workspace-test=.
- =src/treesitter.cpp= — syntax highlighting. A core set of grammars is
  compiled in (see =TS_GRAMMAR_NAMES= in =CMakeLists.txt=); every other
  language is =dlopen()=ed at runtime from =$MEP_TS_PARSER_PATH=.
- =src/regex.cpp= — the dependency-free regex engine behind =/=, =:s=
  and =:g=.

* CAD and finite elements

A second modeler, in the CAD lineage rather than the polygonal one
=model3d_doc.cpp= implements, with a finite-element stack under it. See
[[file:../plans/CAD_FEM_PLAN.md][the plan]], which records what is built
and what is not: Part 0 (foundations), Part A (curves and surfaces),
Part B (the boundary representation), Part C (intersections, the
surface-surface marcher, and boolean operations) and Part D (the
sketcher: geometry, constraint solver, diagnosis, profile extraction and
the interactive =Mode::CadSketch= pane) and Part E (the feature tree,
extrude, revolve, loft, sweep, fillets and chamfers on straight edges
between planar faces, offset/draft/shell/thicken on polyhedra, patterns,
datums and assemblies) and Part F (the native =.mepcad= document, STEP in
and out, IGES in, DXF, STL/OBJ/glTF, drawing views and the =Mode::Cad=
pane) are in the tree. Meshing and the physics are not.

The two modelers share almost nothing on purpose. =MeshData= is float32
parallel arrays with no notion of a face; exact geometry needs doubles,
analytic and NURBS surfaces, and topology that survives a rebuild. They
are designed to meet at exactly one place, the tessellator, and that
bridge is one-way.

| Area | Files |
|------+-------|
| Double-precision math core | =cad_math.{h,cpp}= — vectors (including homogeneous =Vec4d=), matrices, intervals, the per-entity tolerance model, Newton/Brent/Levenberg-Marquardt, one-sided-Jacobi SVD with rank and null space, Gauss-Legendre and adaptive Gauss-Kronrod quadrature |
| Exact geometric predicates | =cad_predicates.{h,cpp}= — filtered-then-exact orientation, in-circle and in-sphere over Shewchuk expansion arithmetic |
| B-spline and NURBS engine | =cad_nurbs.{h,cpp}= — knot vectors, basis functions, evaluation, knot insertion/removal, degree elevation, Bézier decomposition, interpolation and approximation (Piegl & Tiller, algorithm-by-algorithm) |
| Curves | =cad_curve.{h,cpp}= — =Curve3= over Line/Circle/Ellipse/NURBS, point inversion, adaptive tessellation |
| Surfaces | =cad_surface.{h,cpp}= — =Surface= over Plane/Cylinder/Cone/Sphere/Torus/NURBS plus extrusion, revolution, ruled and offset; loft and sweep (rotation-minimizing frames); the fundamental forms and curvatures the mesher needs |
| Mass properties | =cad_mass.{h,cpp}= — volume, area, centroid and inertia by the divergence theorem |
| Boundary representation | =cad_topology.{h,cpp}= — Body/Shell/Face/Loop/CoEdge/Edge/Vertex as flat arrays, plus box, cylinder, sphere and torus primitives |
| Parameter-space curves | =cad_pcurve.{h,cpp}= — each coedge's edge curve in its face's (u,v), including the seam and pole cases |
| Validity checking | =cad_validate.{h,cpp}= — structural, combinatorial (Euler-Poincaré) and geometric checks, with categorised diagnostics |
| Tessellation | =cad_tessellate.{h,cpp}= — watertight triangle meshes by Delaunay in parameter space, over a shared edge sampling; the triangulator uses a vertex at infinity rather than a super-triangle, since a sliver's circumcircle is unbounded relative to the points and a super-triangle inside one leaves holes in the middle of the mesh |
| Persistent naming | =cad_naming.{h,cpp}= — recognising an entity again after a parametric rebuild, and reporting when it cannot |
| Intersections | =cad_intersect.{h,cpp}= — curve/curve, curve/surface, the closed-form surface/surface table for the quadric families, and the marching solver for everything else |
| Point classification | =cad_classify.{h,cpp}= — inside/outside/boundary against a solid, by ray crossing parity |
| Planar arrangements | =cad_arrangement.{h,cpp}= — curves cut at every crossing into a half-edge structure, read back as the regions they bound, with holes attached; shared by the boolean and the sketcher |
| Booleans | =cad_boolean.{h,cpp}= — union, intersection and difference by imprint/classify/stitch, over an arrangement built in each face's own parameter space |
| Sketch geometry | =cad_sketch.{h,cpp}= — 2D geometry on a plane that may be attached to a model face, plus profile extraction with nested holes |
| Feature modeling | =cad_feature.{h,cpp}= — a parametric feature tree replayed from the first dirty feature, the profile-to-solid constructions (extrude, revolve, loft, sweep) each with Add/Cut/Intersect through the boolean, and blends (fillet, chamfer) done as local trim-and-stitch surgery rather than as a boolean, because a corner cutter is made almost entirely of the degeneracies the boolean does not handle |
| Direct modelling | =cad_modify.{h,cpp}= — offset, draft, shell and thicken, which are one routine: change which surface some faces lie on, then re-solve each corner as the meeting of its three faces, leaving the topology alone |
| Patterns | =cad_pattern.{h,cpp}= — linear, grid, circular, mirror and sketch-driven patterns, all of them a list of transforms handed to one copy routine; mirroring turns each face round, and which half of that correction a face needs depends on whether its surface's parameters survived the reflection |
| STEP | =cad_step.h= with =cad_step_parse.cpp= (the ISO 10303-21 grammar, which knows nothing about geometry), =cad_step_read.cpp= (entities onto the B-rep) and =cad_step_write.cpp= (AP214 out, analytic surfaces kept analytic) |
| Other interchange | =cad_exchange.h= with =cad_exchange_mesh.cpp= (STL/OBJ/glTF), =cad_exchange_dxf.cpp= (2D sketches, geometry only — DXF cannot carry constraints) and =cad_exchange_iges.cpp= (IGES B-rep in; not written, since STEP says the same things better) |
| Drawing views | =cad_drawing.{h,cpp}= — edges projected with hidden-line removal by sampling against the tessellation, out as SVG |
| The CAD pane | =Mode::Cad= and =CadSession= in =editor.h=; the feature-tree outliner and the software-shaded view in =main.cpp= — the same =Editor::Cad*= methods the =mep.cad_*= Lua functions and the =cad.*= agent-RPC methods call |
| Native CAD document | =cad_doc.{h,cpp}= — =.mepcad=: the feature tree, its sketches and its persistent names as versioned text. The only lossless format, because it stores the operations rather than the body they produced |
| Datums and assemblies | =cad_assembly.{h,cpp}= — datum points/axes/planes, part instances and mates, solved as least squares over quaternion placements by the same dual-number machinery the sketcher uses; the degree-of-freedom count comes from the Jacobian's rank. Parts may be feature trees, so a dimension change rebuilds them and the mates re-find their faces by name; sub-assemblies are placed rigidly and solved innermost first |
| Exact derivatives | =cad_dual.h= — forward-mode dual numbers, so writing a residual writes its Jacobian row; shared by the sketch solver and the assembly solver |
| Constraint solver | =cad_constraint.{h,cpp}= — sixteen constraint kinds as least squares with dual-number Jacobians, cluster decomposition, DOF and null-space diagnosis, redundant-versus-conflicting discrimination, dragging |
| The sketch pane | =Mode::CadSketch= and =CadSketchSession= in =editor.h=; input in =editor.cpp=, drawing and the mouse in =main.cpp= — the same =Editor::CadSketch*= methods the =mep.sketch_*= Lua functions and the =sketch.*= agent-RPC methods call, so a sketch drawn by hand and one built by a script take the same path |
| Meshing | =fem_mesh.h= with =fem_mesh_size.cpp= (an octree sizing field seeded from curvature, thin walls and local overrides, graded by a Lipschitz condition), =fem_mesh_surface.cpp= (per-face Delaunay refinement in the face's own parameters, under the metric its first fundamental form induces, with shared edges meshed once) and =fem_mesh_volume.cpp= (Bowyer–Watson tetrahedralisation and quality measurement; boundary recovery still to come) |
| Sparse linear algebra | =num_sparse.{h,cpp}= — CSR, fill-reducing orderings, sparse =LDL^T=, IC(0), CG, GMRES |
| FEM model and solver | =fem_model.{h,cpp}= (mesh, materials, constraints, loads, JSON), =fem_solve.{h,cpp}= (Hex8 elasticity, assembly, direct and iterative solution, stress recovery) |
| Result visualization | =fem_viz.{h,cpp}= — surface extraction, colour maps, deformed-shape meshes |
| The solver process | =fem_server.cpp= → the =mep-fem= binary |

=mep-fem= is a separate process for the same reasons the language servers
are: =src/job.h= only ever fires callbacks on the main thread so editor
state needs no synchronization, and a solve is the one operation here that
can legitimately run for minutes and allocate gigabytes. It speaks
JSON-RPC over stdio through the same =rpc_framing.h= everything else uses,
and =mep-fem --solve <file>= runs it headless for CI.

Two build details that are load-bearing:

- =cad_predicates.cpp= is compiled with =-ffp-contract=off=. Its exact
  arithmetic assumes every floating-point operation is individually
  rounded; a fused multiply-add would break the error terms silently.
  =PredicatesSelfTest()= is the runtime backstop if the flag is ever lost.
- The analytic curves and surfaces stay first-class rather than being
  converted to NURBS on sight. Each can produce its *exact* NURBS form on
  demand, but that conversion preserves shape, not parameterization inside
  a span — see =Curve3::ToNurbs='s own note, which matters for anything
  pairing parameters across the two.
- =gfx::Mesh::indices= is 32-bit. It was =unsigned short=, and every
  importer worked around the 65,536-vertex cap by abandoning indexing
  altogether — which also destroys the vertex sharing a per-vertex result
  field needs to interpolate smoothly.

Tests: =mep-cad-math-test=, =mep-cad-predicates-test=,
=mep-cad-nurbs-test=, =mep-cad-curve-test=, =mep-cad-surface-test=,
=mep-cad-mass-test=, =mep-cad-topology-test=, =mep-num-sparse-test= and
=mep-fem-test= are windowless and run by =just test=;
=mep-gfx-native-index32-smoke=, =mep-gfx-native-fem-smoke= and
=mep-gfx-native-brep-smoke= need a display and render to a PNG.

* Language servers

mep is an LSP *client* for around thirty-eight servers (=kBuiltinLsp= in
=main.cpp=; the registry is plain data, so =init.lua= can extend it), and
ships two *servers* of its own:

- =src/org_lsp.cpp= — org-mode diagnostics, completion, hover, document
  symbols, folding and definition, as pure functions over plain lines.
- =src/org_lsp_server.cpp= — the =mep-org-lsp= binary wrapping those in
  stdio JSON-RPC. mep spawns it out of its own bin directory, so org
  files get diagnostics with nothing installed; it also runs standalone
  in any other LSP client.
- =src/r_lsp_parse.cpp= — a hand-written R lexer and parser (the whole
  language: precedence, every assignment form, =[[= subscripts, formulas,
  lambdas), recovering per statement so a half-typed file still has an
  outline.
- =src/r_lsp.cpp= — R scope resolution on top of that, and from it
  diagnostics, completion, hover, symbols, folding, definition,
  references and signature help. =src/r_lsp_vocab.cpp= holds the curated
  signatures and documentation; =src/r_lsp_base_names.cpp= is generated
  by =scripts/gen_r_names.R= from a real R installation and committed, so
  the build (and the server) need no R at all.
- =src/r_lsp_server.cpp= — the =mep-r-lsp= binary, same stdio shape as
  the org one. Nothing in it starts R or evaluates the document.
- =src/python_ast.cpp= — a Python 3 tokenizer and recursive-descent
  parser. Unlike the org server, the Python one needs a real syntax tree:
  its interesting questions ("is this name ever defined?", "is this
  import used?") are about scopes.
- =src/python_lsp.cpp= — the scope model and every feature over it, again
  as pure functions over plain lines; =src/python_lsp_vocab.cpp= is the
  standard-library table it answers from, generated once and committed so
  no Python installation is needed.
- =src/python_lsp_server.cpp= — the =mep-python-lsp= binary, the same
  stdio JSON-RPC shape as the org one. It claims =py= in the registry;
  pyright stays registered without a filetype.
- =src/cpp_ast.{h,cpp}= and =src/cpp_parse.cpp= — the C++ front end: a
  tokenizer, a *modelled* preprocessor (conditional groups are resolved
  against the macros the file defines plus a host-shaped predefined set,
  and only the surviving branch reaches the parser) and a
  recursive-descent parser whose three ambiguity heuristics are
  documented where they are made.
- =src/cpp_lsp.cpp=, =src/cpp_lsp_diagnostics.cpp= and
  =src/cpp_lsp_features.cpp= — the scope model, the checks and everything
  that is not a check. This is the one server that reads another file: a
  quoted =#include= that resolves next to the document is parsed too and
  cached by modification time, which is what makes go to definition land
  in a project's own header.
- =src/cpp_lsp_vocab.cpp= and =src/cpp_lsp_std_names.cpp= — the curated
  vocabulary and a 4,000-name standard-library list generated from the
  real headers by =scripts/gen_cpp_std_names.sh= (which extracts them
  with mep's own parser) and committed, so no compiler headers are needed
  to build.
- =src/cpp_lsp_server.cpp= — the =mep-cpp-lsp= binary. It claims the C++
  filetypes, =h= among them: a =.h= is a C++ header far more often than
  not, and this front end reads C too.
- =src/c_ast.cpp= — a C lexer, preprocessor model and recursive-descent
  parser. The preprocessor is the part with no Python counterpart: it is
  never *run*, because an editor sees unpreprocessed source and a server
  that needed =-I= flags would say nothing in most buffers. Instead each
  =#if= group contributes one arm, chosen by evaluating the condition
  where the file settles it and by bracket balance where it does not.
- =src/c_lsp.cpp= — the scope model and every feature over it, again as
  pure functions over plain lines; =src/c_lsp_vocab.cpp= holds the
  keywords and the prose, and =src/c_lsp_std_names.cpp= the standard
  library's real declarations, read out of the real headers by
  =scripts/gen_c_names.py= and committed so no compiler is needed to
  build.
- =src/c_lsp_server.cpp= — the =mep-c-lsp= binary, the same stdio
  JSON-RPC shape again. It claims =c= in the registry — =h= goes to the
  C++ server above — and clangd stays registered without a filetype.
- =src/maxima_ast.cpp= — a Maxima lexer and Pratt parser. The binding
  powers are not invented: they are the =lbp=/=rbp= properties Maxima's
  own =src/nparse.lisp= sets, read out of a live image, which is why the
  parse agrees with the language on =-x^2=, on =a : b : c= and on =for
  i : 1= meaning =for i from 1=. A file may extend its own grammar
  (=infix("~")=), so the source is scanned for those declarations, and
  for the =load= of a shipped package that carries them, before it is
  read for real.
- =src/maxima_lsp.cpp= — the scope model and every feature over it.
  =src/maxima_lsp_vocab.cpp= holds the prose, and
  =src/maxima_lsp_builtin_names.cpp= the 2,846 documented names with
  their kinds and argument lists, generated by
  =scripts/gen_maxima_names.py= from a real Maxima's own documentation
  index and committed, so neither the build nor the server needs Maxima.
  What it does *not* report is as deliberate as what it does: in a
  computer-algebra system an unbound name is an algebraic unknown and a
  call to an undefined function is a noun expression, so there is no
  undefined-name check at all.
- =src/maxima_lsp_server.cpp= — the =mep-maxima-lsp= binary, the same
  stdio JSON-RPC shape again. It claims =mac=, =dem=, =mc= and =max=;
  there is no third-party Maxima server to defer to.

Code *inside* a =#+begin_src= block is handled separately, by
=kBuiltinOrgPolyglot='s per-block shadow buffers talking to a real server
for that language. Both publish against the same org file and their
diagnostics are merged (=mep_org_diag_set=).

* The wasm build and its launcher

=just run-wasm= builds the Emscripten target and opens it in a native
window through Deno + [[https://github.com/webview/webview_deno][webview]]. =build/web/mep.html= is opened directly
over =file://= rather than served: the wasm is embedded into the page
(=-sSINGLE_FILE=1=), so there is no separate =.wasm= fetch a =file://=
origin would have to make, and the window opens with no server setup at
all.

File I/O is the part a browser cannot do, so it goes through a bridge.
=:e=/=:w=/=:source= in the wasm build make a synchronous
=XMLHttpRequest= to a loopback-only HTTP server (=launcher/serve.ts=)
that does the real read/write, from =EM_JS= calls in =src/editor.cpp=.
Synchronous XHR rather than an awaited =fetch()= specifically so
Emscripten's Asyncify never has to be linked — see the comment above
=mep_js_read_file= for the full reasoning. Opening =build/web/mep.html=
in an ordinary browser tab has no such server behind it and no
=?bridgePort=...= in its URL, so those commands fail with a plain
read/write error there, exactly as native file I/O is simply unavailable
in that context.

The bridge does not use =webview.bind()=, despite that being the more
obvious choice. =webview_run()= — the call that pumps the window for as
long as it is open — is a plain *synchronous* Deno FFI call, and it
blocks its entire isolate's event loop for that whole duration: nothing
async in that isolate, including a =bind()= callback's own
=await Deno.writeTextFile(...)= settling and its reply reaching the page,
reliably progresses while it runs. Confirmed concretely — even a =curl=
from outside the process to an HTTP server started in the *same* script
as =webview.run()= hung indefinitely with the window open.
=launcher/webview_worker.ts= therefore isolates =webview.run()= in its own
Deno Worker (a separate OS thread with its own V8 isolate), so
=serve.ts='s HTTP server on the main thread stays entirely free of that
block and the page's requests reach it as ordinary loopback HTTP.

- =web/shell.html= — the minimal HTML shell the wasm build is embedded
  into; also reads the file-bridge port from the page's URL query string.
- =launcher/serve.ts= — main thread: the loopback-only file-bridge HTTP
  server, which then hands off to =webview_worker.ts=.
- =launcher/webview_worker.ts= — the worker that owns =webview.run()=.
