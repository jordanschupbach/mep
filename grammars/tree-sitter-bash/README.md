# tree-sitter-bash

A [tree-sitter](https://tree-sitter.github.io/) grammar for **Bash**, written
for mep and compiled into it, so `.sh`, `.bash` and `.zsh` files are
highlighted, folded and outlined without a grammar `.so` on the machine. It
follows the Bash 5.3 reference manual (shell syntax, commands, functions,
parameters, expansions, redirections, conditional expressions, arithmetic)
and `parse.y`.

Its node names, fields and tree shapes are the ones
[tree-sitter/tree-sitter-bash](https://github.com/tree-sitter/tree-sitter-bash)
0.25 established -- the grammar mep loaded dynamically before this one -- so
queries and tools written for that grammar work unchanged: the same 59 node
types and 19 fields, and the same rule order (where two readings survive to
the same point, tree-sitter keeps the one whose nodes are numbered lower).

| File | What it is |
|---|---|
| `grammar.js` | the grammar |
| `src/scanner.c` | the hand-written external scanner (below) |
| `src/parser.c`, `src/grammar.json`, `src/node-types.json`, `src/tree_sitter/` | generated by `just bash-grammar` (mep-ts-generate) -- commit them, don't edit them |
| `queries/highlights.scm` | highlight captures (nvim-treesitter naming) |
| `queries/folds.scm` | fold ranges |
| `queries/structure.scm` | the structure sidebar's outline: functions, top-level `readonly`/`export`/`declare` settings and ALL_CAPS assignments |
| `test/corpus/*.txt` | corpus cases, run by `mep-ts-corpus-test` |
| `test/known-differences.txt` | reviewed files where the trees differ from the old grammar's |

## Why a scanner

The shell's lexer depends on what the parser expects next, which only the
parser knows (it says so through `valid_symbols`):

* **Here-documents**: `<<EOF` opens a body that starts after the line ends.
  The scanner keeps a stack of pending delimiters (a line may open several),
  each with whether it is quoted (no expansions in the body) and whether
  `<<-` strips tabs. The stack is serialized, so an incremental reparse
  restores it.
* **Names**: `x` is a `variable_name` only before `=`, `+=`, `[` or an
  operator inside `${...}`; otherwise it is a word.
* **Words that are operators**: `-f` in `[[ ]]`, `}` closing `${...}` or a
  word character, `{1..3}` versus `{fd}>file`.
* **Patterns and regexes**: the right of `=~` (ends at an unbracketed
  blank), `${x/pattern/...}` (ends at `/`), `${x%pattern}` (ends at the
  brace), extglob patterns in `case` and `[[ == ]]`. Bracket expressions
  are opaque (`[^]]`, `[{(]` are characters).

The order the scanner tries token families in is load-bearing; it is the
order the old scanner used, restructured as one function per family.

## How it compares

`just grammar-corpus bash` collects 3,616 files (485k lines): bash-completion,
git's test suite, bash's own examples and tests, every `.sh` in nixpkgs,
bats, asdf and dehydrated, and the repository's own scripts. Against
tree-sitter-bash 0.25.1 (`just grammar-diff bash --old <its src> --old-clean`):

* 3,352 files parse to identical trees. Every file and every top-level item
  the old grammar parsed without errors is identical, except the 82 files
  in `test/known-differences.txt`, each one the old grammar misreading code
  bash accepts (below).
* Files with parse errors: 354 -> 232, none new. Of the files `bash -n`
  accepts, the old grammar failed on 259 and this one on 116 -- 87 of those
  are bash's own test suite, which exercises corners on purpose (`${ cmd; }`
  function substitution, `cat <<A <<B`, `((` as nested subshells).
* Bytes inside ERROR nodes: 17% fewer on the corpus, 1.4% fewer on 3,000
  damaged copies (`just grammar-recovery bash`).
* The scanner is clean under ASan + UBSan on the corpus plus 3,000 damaged
  copies (`just grammar-fuzz bash`).

### Fixed

What bash accepts and the old grammar got wrong:

* `a | b | c && d` was `a | (b | c && d)`, and a line `x && y` after a
  three-stage pipeline was swallowed into its last command as arguments
  (no error, so nothing showed it). `|` binds tighter than `&&`/`||`.
* Extglob patterns after a prefix (`*.@(jpg|png)`, `--@(a|b)`,
  `-${opts}@([ab]|c*)`), with brackets or quotes or blanks inside a group
  (`@(help|[h?])`, `@(x|'')`, `?( *)`), or on a continuation line.
* nixpkgs `@placeholder@` words as commands and arguments.
* `<>` and named-descriptor (`{fd}>file`) redirections; `for name do`;
  `for x in ; do`; here-strings after any compound command; `10#$n`;
  `${a[@]:$n}`; `[ \( a -o b \) ]`; `${x:+ (text)}` and `${x:+$x;}`.
* Escapes in patterns (`*\\'[<>]'*`, `${x#*\'}`), ANSI-C quoting in
  `${x%$'a\'b'}`, bracket expressions in regexes (`[^]]*`, `[<{().[]`).

### Still open

Shared with the old grammar: more than one here-document on a line, bash
5.3's `${ cmd; }` and `${| cmd; }`, `((` meaning two nested subshells,
nixpkgs templates inside `${...}` (`${NAME_@salt@:-}`), zsh-only syntax.
`$"text"` as an argument reads as a plain string (as before).
