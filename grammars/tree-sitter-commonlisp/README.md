# tree-sitter-commonlisp

A [tree-sitter](https://tree-sitter.github.io/) grammar for Common Lisp,
written for mep and compiled into it, so `.lisp`, `.lsp`, `.cl` and `.asd`
files are highlighted, folded and outlined without a grammar `.so` on the
machine. It follows the Common Lisp reader as the standard defines it
(CLHS chapter 2: syntax types, token interpretation, the standard macro
characters).

| File | What it is |
|---|---|
| `grammar.js` | the grammar |
| `src/scanner.c` | the hand-written external scanner: nestable block comments, string text |
| `src/parser.c`, `src/grammar.json`, `src/node-types.json`, `src/tree_sitter/` | generated by `just commonlisp-grammar` (mep-ts-generate) -- commit them, don't edit them |
| `queries/highlights.scm` | highlight captures (nvim-treesitter naming) |
| `queries/folds.scm` | fold ranges |
| `queries/structure.scm` | the structure sidebar's outline: packages, classes, structures, functions, macros, methods, variables |
| `test/corpus/*.txt` | corpus cases, run by `mep-ts-corpus-test` |

## The tree is the reader's

Common Lisp has no syntax beyond what the reader reads. A `defun` is a list
whose first element is the symbol `DEFUN`, so the tree has lists, atoms and
the reader macros' forms -- `quote`, `quasiquote`, `unquote`,
`unquote_splicing`, `function` (`#'`), `vector`, `feature_expression`
(`#+`/`#-`), `read_eval` (`#.`), `label`/`label_reference` (`#1=`/`#1#`),
`array` (`#2A`), `structure` (`#S`), `complex` (`#C`), `pathname` (`#P`),
`bit_vector` (`#*`) -- and no `defun` node. What a list means is decided by
the queries, from the operator's name. That keeps the grammar honest about
user macros: a `define-foo` reads exactly like a `defun`, as it does for the
reader.

Atoms: `symbol`, `qualified_symbol` (a `package` and a `symbol`, for
`pkg:sym` and `pkg::sym`), `keyword`, `uninterned_symbol` (`#:foo`),
`number` (integers, ratios, floats with any exponent marker, `#x`/`#b`/
`#o`/`#nR` rationals), `string` (with `escape_sequence` and
`format_directive` children), `character` (`#\a`, `#\Space`).

SBCL's extended package prefix, `sb-impl::(a b c)`, is a `package_form`:
SBCL's own sources use it throughout.

## Why a scanner

* **Block comments nest**: `#| a #| b |# c |#` is one comment.
* **String text** is read by the scanner too, so that the block comment --
  an extra, valid everywhere -- is never recognized inside a string:
  `"#|"` is a string. The string's text being a valid token is how the
  scanner knows it is inside one.

A `~` in a string starts a `format_directive` except just before the
closing quote or an escape (`"~"`, `"\"~\""`), where it directs nothing.

## Lexing notes

* `12` is a number and `1+` a symbol: the longer match wins, and on a tie
  of equal length the rule listed first (`number`) does.
* The package and its colons are one token, so `foo:bar` is never read as
  the symbol `foo` followed by the keyword `:bar`.
* A lone `.` is the consing `dot` of `(a . b)`, never a symbol.

## Checked against

The sources of SBCL 2.5.10 (compiler, runtime library, contribs, tests) and
of alexandria, cl-ppcre, iterate, trivia, cffi and fiveam -- 1,521 files,
700,744 lines (`just grammar-corpus commonlisp`). 1,512 parse with no
errors; the other 9 use reader macros a file installs for itself (`#L`,
`#[`, `#_`, `#"`, `#@`), are SBCL tests of malformed input, or are UTF-16.
The scanner is clean under ASan + UBSan on those files and 3,000 damaged
copies (`just grammar-fuzz commonlisp`).
