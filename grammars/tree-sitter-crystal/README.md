# tree-sitter-crystal

A [tree-sitter](https://tree-sitter.github.io/) grammar for **Crystal**,
written for mep and compiled into it, so `.cr` files are highlighted,
folded and outlined without a grammar `.so` on the machine. It follows the
Crystal language reference and the compiler's own hand-written lexer and
parser (`src/compiler/crystal/syntax/lexer.cr`, `parser.cr`).

Its node names, fields and tree shapes are the ones
[crystal-lang-tools/tree-sitter-crystal](https://github.com/crystal-lang-tools/tree-sitter-crystal)
established -- the grammar mep loaded dynamically before this one -- so
queries and tools written for that grammar work unchanged: the same 152
named node types and 41 fields, and the same rule order (where two readings
survive to the same point, tree-sitter keeps the lower-numbered one, so
order matters; keep new rules after the ones they could compete with).

| File | What it is |
|---|---|
| `grammar.js` | the grammar |
| `src/scanner.c` | the external scanner: the tokens whose reading depends on what the parser expects next |
| `src/parser.c`, `src/grammar.json`, `src/node-types.json`, `src/tree_sitter/` | generated by `just crystal-grammar` (mep-ts-generate) -- commit them, don't edit them |
| `queries/highlights.scm` | highlight captures (nvim-treesitter naming) |
| `queries/folds.scm` | fold ranges |
| `queries/structure.scm` | the structure sidebar's outline: modules, classes, structs, enums (and their members), annotations, aliases, methods, macros, `lib` with its `fun`/`struct`/`union`/`type`, constants |
| `test/corpus/*.txt` | corpus cases, run by `mep-ts-corpus-test` |

## Why there is a scanner

Crystal's lexer leans on the parser far more than a context-free lexer
allows: whether `{` opens a block, a tuple or a tuple type; whether `/`
divides or starts a regex; whether `-x` is unary; whether `if` starts a
statement or is a suffix; where a heredoc body, a `%`-literal or a macro
body ends. `src/scanner.c` reads those tokens, using tree-sitter's valid
symbols as the parser's expectation.

## How it compares

`just grammar-corpus crystal` collects 4,602 files: the Crystal compiler,
standard library and spec suite, plus crystalline, ameba, invidious, mint,
lucky-cli, shards, gi-crystal and the other Crystal projects nixpkgs
packages, with their bundled shards. Against the upstream grammar (`just
grammar-diff crystal --old <its src>`): all 4,602 files parse to identical
trees; the same 73 files have parse errors in both. Error recovery on 3,000
damaged copies is the same to the byte, and the parser is clean under ASan
+ UBSan on the corpus and the damaged copies (`just grammar-fuzz crystal`).

The oracle (`--oracle`) is the compiler's own parser, through `crystal tool
format` (`tools/ts_grammar_diff/crystal_check.sh`).

## Known limits (shared with the grammar it replaces)

* A highlighter's grammar, not a compiler: it reads some things Crystal
  rejects, and the 73 files above use corners it does not cover. mep's
  Crystal language server (a port of the compiler's parser) reports the
  real syntax errors.
* Macro code (`{{ }}`, `{% %}`) is parsed as far as it is Crystal; macro
  text that only becomes Crystal after expansion is not.
