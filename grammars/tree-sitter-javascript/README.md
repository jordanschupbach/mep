# tree-sitter-javascript

A [tree-sitter](https://tree-sitter.github.io/) grammar for **JavaScript**,
written for mep and compiled into it. It follows ECMA-262 (2025: Annex A's
grammar summary and the §12 lexical grammar), Annex B's HTML-like comments
(`<!--` and `-->` at the start of a line), the stage-3 decorators and
`using` declarations, and JSX.

Its node names, fields and tree shapes are the ones
[tree-sitter/tree-sitter-javascript](https://github.com/tree-sitter/tree-sitter-javascript)
0.25 established -- the grammar mep vendored before this one -- so queries
and tools written for that grammar work unchanged: the same 114 node types
and 36 fields.

## How it compares

`just grammar-diff javascript --oracle`, on Node 22's `lib/` (and the
`lib/` of the packages it bundles under `deps/`), three React front ends
for JSX (homepage-dashboard, navidrome and Mastodon), and the JavaScript in
this repository (2,096 files, 585 of them `.jsx`; 371k lines):

* 2,093 files parse to identical trees. The other 3 are listed in
  `test/known-differences.txt`, all for one bug in the old grammar, below.
* Both grammars fail on the same 6 files, which the language accepts, for
  two shared limitations, worth fixing if they come up more:
  * **A JSX attribute named by a reserved word right after the tag name**
    (`<Collapse in={open}>`, 5 navidrome files). JSX attribute names are
    any IdentifierName, and `<C a={1} in={2}>` parses, but in the state
    just after the tag name the keyword `in` is lexed. Putting the
    attribute list under the `properties` reserved-word context (as
    `a.class` is) is not enough: `in` then lexes as an identifier the state
    has no action for.
  * **An arrow function's `{}` body followed by a line starting with `[`**
    (npm's `base-cmd.js`): `const f = () => {...}` then `[...a].forEach(...)`.
    An arrow function cannot be subscripted, so §12.10 inserts a semicolon;
    the scanner, which cannot see that the `}` closed an arrow body, does
    not.

**The difference: `await` in async code.** `await` is reserved inside
async functions, and AwaitExpression has no line-terminator restriction
(§15.8). The old grammar read `await (async () => {...})()` as a call of a
function named `await`, and a line holding only `await` as the name
`await` ended by a semicolon, leaving the next line's call unawaited. Here
both are an `await_expression` of the call.

**Error recovery** (`just grammar-recovery javascript`): on 3,000 damaged
copies of the corpus, 5.2% fewer bytes end up inside ERROR nodes than with
the old grammar (better in 66 files, worse in 84). As for Python, the
language's reserved words are tree-sitter `reserved` keywords, so `if` or
`function` is never read as a name and recovery resynchronizes on them;
property names (`a.class`, `{default: 1}`) take any of them.

The scanner is clean under ASan + UBSan on the corpus plus the 3,000
damaged copies (`just grammar-fuzz javascript`).

## Files

| File | What it is |
|---|---|
| `grammar.js` | the grammar |
| `src/scanner.c` | the external scanner: automatic semicolons, template text, `?`, HTML-like comments, JSX text |
| `src/parser.c`, `src/grammar.json`, `src/node-types.json`, `src/tree_sitter/` | generated by `just javascript-grammar` (mep-ts-generate) -- commit them, don't edit them |
| `queries/highlights.scm` | highlight captures (nvim-treesitter naming); TypeScript's query is layered over its first part |
| `queries/folds.scm` | fold ranges |
| `queries/structure.scm` | the structure sidebar's outline: classes, functions, methods, function-valued fields, assignments and object members, top-level ALL_CAPS constants |
| `test/corpus/*.txt` | corpus cases, run by `mep-ts-corpus-test` |
| `test/known-differences.txt` | the reviewed differences from the old grammar, for `just grammar-diff` |

The scanner keeps no state, so incremental reparses need nothing saved.
It decides what ECMA-262 leaves to context. An automatic semicolon is a
zero-width `;` where a line break, a `}` or the end of input ends a
statement the next token could not continue. The parser tells it the rest
by which tokens it marks valid: `||` valid means a statement may end in an
expression here (so `-->` is an operator, not a comment), and
`escape_sequence` or `regex_pattern` valid means it is inside a string,
template or regex (where `<!--` is text).

Rules are declared in the old grammar's order, which is load-bearing (see
`grammar.js`'s header, and the Python grammar's README).

`highlights.scm` serves TypeScript too: `.ts` and `.tsx` files (whose
grammars are loaded dynamically) get its first part with TypeScript's own
query on top, so its first part may name only nodes and shapes
tree-sitter-typescript also has. Two trailing sections are cut off by
their headers (`treesitter.cpp`'s `LayeredTypescriptHighlights`):
"JavaScript only" (bare parameters, which TypeScript wraps) for both, and
"JSX" for `.ts`.

## Working on it

```sh
just javascript-grammar                  # regenerate src/parser.c and run the corpus tests
just grammar-corpus javascript           # once
just grammar-diff javascript --oracle    # must report 0 unexplained differences
just grammar-recovery javascript         # the error-bytes total should not grow
just grammar-fuzz javascript
```

The oracle is `node --check`, and esbuild for `.jsx` (Node rejects JSX).

Then rebuild mep, which compiles `src/` directly (`ts_javascript` in
CMakeLists.txt) and embeds the queries into a generated header at
configure time. `mep-treesitter-test` checks highlights, folds, the
outline and incremental reparsing (comments, templates and JSX elements
opened and closed by edits).
