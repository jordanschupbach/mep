# tree-sitter-markdown

A [tree-sitter](https://tree-sitter.github.io/) grammar for **Markdown's
block structure**, written for mep and compiled into it. It follows
CommonMark 0.31 (spec.commonmark.org) and GFM 0.29's pipe tables and task
lists, plus YAML (`---`) and TOML (`+++`) front matter. Its partner,
`../tree-sitter-markdown_inline`, parses the inline content (emphasis,
links, code spans): mep runs it over each `inline` node this grammar
leaves, with `ts_parser_set_included_ranges` (treesitter.cpp's
`CollectMarkdownInlineSpans`).

Its node names, fields and tree shapes are the ones
[tree-sitter-grammars/tree-sitter-markdown](https://github.com/tree-sitter-grammars/tree-sitter-markdown)
0.5 established -- the grammar mep vendored before this one -- so queries
and tools written for it work unchanged: the same 51 node types and the
`heading_content` field, and the same rules in the same order.

## How it compares

`just grammar-diff markdown --oracle`, on the repository's Markdown, cmark's
and Node 22's docs, and every example of the CommonMark and GFM specs and
their regression and extension tests, one file each (1,609 files, 228k
lines):

* 1,607 files parse to identical trees. The other 2 are listed in
  `test/known-differences.txt`: this grammar follows CommonMark 0.31 where
  the old one followed an earlier version.
  * `<textarea>` opens an HTML block like `<pre>` (§4.6, new in 0.31).
  * An ordered list may interrupt a paragraph only if it starts at 1
    (§5.2). The old scanner let any one-digit number do it.
* The oracle is structural: Markdown accepts any text, so `--oracle`
  compares the blocks of each differing file -- paragraphs, headings and
  their levels, lists, items, quotes, code, HTML, rules, tables -- with
  what cmark-gfm (and cmark 0.31) read, and fails if only the old grammar
  agrees. Both differences agree with cmark. Across the whole corpus the
  new grammar's blocks agree with cmark on 1,588 of 1,609 files (the old
  one's on 1,586); the rest are shared.

Two more changes follow CommonMark 0.31 without showing in the corpus:
`<!doctype html>` (a lower-case declaration) opens an HTML block, which the
old grammar got only by reading it as a tag; and front matter is tried
before a thematic break, as before.

**Error recovery** (`just grammar-recovery markdown`): the same bytes in
ERROR nodes as the old grammar on 3,000 damaged copies of the corpus.
Markdown has almost no errors: any text is a document.

The scanner is clean under ASan + UBSan on the corpus plus the 3,000
damaged copies (`just grammar-fuzz markdown`).

## Files

| File | What it is |
|---|---|
| `grammar.js` | the grammar |
| `common.js`, `html_entities.json` | the rules both Markdown grammars share (escapes, entity and character references, link labels, destinations and titles), and HTML5's entity names |
| `src/scanner.c` | the external scanner: the open-block stack, block starts, soft and hard line breaks |
| `src/parser.c`, `src/grammar.json`, `src/node-types.json`, `src/tree_sitter/` | generated by `just markdown-grammar` (mep-ts-generate) -- commit them, don't edit them |
| `queries/highlights.scm` | highlight captures (nvim-treesitter naming) |
| `queries/structure.scm` | the structure sidebar's outline: ATX and setext headings, `heading1`..`heading6` |
| `test/corpus/*.txt` | corpus cases, run by `mep-ts-corpus-test` |
| `test/known-differences.txt` | the reviewed differences from the old grammar, for `just grammar-diff` |

Markdown has no fold query: mep folds it by headings with main.cpp's
line-based provider.

### The scanner

The scanner keeps the stack of open container blocks -- block quotes, list
items (with the column their content starts at), indented and fenced
code, HTML blocks -- and at every line's start matches them in order: a
quote by its `>`, an item or indented code by enough indentation. Each
matched block is a `block_continuation` token; the first that does not
match is closed (`_block_close`), unless the line break before was inside
a paragraph, which a lazy line continues.

A line ending is the other decision: inside a paragraph it is soft (the
paragraph goes on) if the next line, its containers matched, would not
start a block that may interrupt a paragraph. The scanner answers that by
reading ahead in a "simulate" mode that moves neither the token's end nor
the stack.

Tabs count to the next multiple of four columns (§2.2); a tab can be split
between two tokens (the end of a list marker and the start of indented
code), so the unused part of consumed indentation is carried over. The
stack and the rest of the state are saved with every token, one byte per
block (the old scanner used four and did not check the buffer's size).

## Working on it

```sh
just markdown-grammar                  # regenerate src/parser.c and run the corpus tests
just grammar-corpus markdown           # once; the spec examples are split out of cmark's sources
just grammar-diff markdown --oracle    # must report 0 unexplained differences
just grammar-recovery markdown
just grammar-fuzz markdown
```

A change to `common.js` changes the inline grammar too: regenerate both
(`just markdown-grammar markdown_inline-grammar`) and diff both.

Then rebuild mep, which compiles `src/` directly (`ts_markdown` in
CMakeLists.txt) and embeds the queries into a generated header at
configure time. `mep-treesitter-test` checks highlights (block and inline),
the outline and incremental reparsing (quotes, nested lists and fences
opened and closed by edits).
