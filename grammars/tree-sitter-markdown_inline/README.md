# tree-sitter-markdown_inline

A [tree-sitter](https://tree-sitter.github.io/) grammar for **Markdown's
inline content**, written for mep and compiled into it: emphasis and
strong emphasis, code spans, links (inline, full, collapsed and shortcut
reference), images, autolinks, raw HTML, entity and character references,
escapes and hard line breaks (CommonMark 0.31 §6), GFM 0.29's
strikethrough, and `$` LaTeX spans.

mep never parses a whole file with it: `../tree-sitter-markdown` reads the
block structure, and this grammar runs over each `inline` node that one
leaves, one range at a time (`ts_parser_set_included_ranges`;
treesitter.cpp's `CollectMarkdownInlineSpans`). The shared rules (escapes,
references, link labels, destinations, titles) are in
`../tree-sitter-markdown/common.js`.

Its node names and tree shapes are the ones
[tree-sitter-grammars/tree-sitter-markdown](https://github.com/tree-sitter-grammars/tree-sitter-markdown)
0.5's inline grammar established -- the grammar mep vendored before this
one -- so queries written for it work unchanged: the same 26 node types,
and the same rules in the same order.

## How it compares

`just grammar-diff markdown_inline`, on the Markdown corpus (1,609 files),
each grammar run over the same `inline` ranges (taken from the old block
grammar, so a difference is this grammar's own; tools/ts_grammar_diff's
`RANGES_FROM`):

* 1,607 files parse to identical trees. The other 2 are listed in
  `test/known-differences.txt`: a declaration is `<!`, a letter, anything
  but `>`, and `>` (§6.6 in 0.31; 0.29 wanted a blank after the name), so
  `<!A>` and `<!x>` are raw HTML, as cmark's regression tests expect.
* The same error bytes on 3,000 damaged copies (`just grammar-recovery
  markdown_inline`), and a scanner clean under ASan + UBSan on them
  (`just grammar-fuzz markdown_inline`).

## Files

| File | What it is |
|---|---|
| `grammar.js` | the grammar; `addInlineRules` generates the inline-content rule families |
| `src/scanner.c` | the external scanner: delimiter runs, code and LaTeX spans |
| `src/parser.c`, `src/grammar.json`, `src/node-types.json`, `src/tree_sitter/` | generated by `just markdown_inline-grammar` (mep-ts-generate) -- commit them, don't edit them |
| `queries/highlights.scm` | highlight captures (nvim-treesitter naming) |
| `test/corpus/*.txt` | corpus cases, run by `mep-ts-corpus-test` (whole inputs, not ranges) |
| `test/known-differences.txt` | the reviewed differences from the old grammar, for `just grammar-diff` |

Emphasis is the hard part (§6.2's delimiter runs): whether a `*` or `_`
opens or closes depends on the characters around it. The grammar tells the
scanner about the token before: `_last_token_whitespace` and
`_last_token_punctuation` are never produced, but are valid right after
whitespace and punctuation, so the scanner sees which in `valid_symbols`.
The scanner looks at the character after the run, decides open or close
for the whole run, and emits each of its characters as a token with that
decision. Contexts that may not hold a delimiter of one kind (an
emphasis's content, link text) are separate rule families.

A code span's (or LaTeX span's) opening run is one only if a run of the
same length follows in the range; otherwise it is text (`_unclosed_span`).

Dynamic precedences are the old grammar's, read from its parse tables
(each REDUCE action carries its production's): they rank the readings of
`[a][b](c)` and the like, and every link and image kind's value matters.

## Working on it

```sh
just markdown_inline-grammar             # regenerate src/parser.c and run the corpus tests
just grammar-diff markdown_inline        # must report 0 unexplained differences
just grammar-recovery markdown_inline
just grammar-fuzz markdown_inline
```

Then rebuild mep (`ts_markdown_inline` in CMakeLists.txt).
