* The keys

All on the =z= prefix, as in Vim. A fold at the cursor means one whose
range covers the cursor's row; where a nest of them does, /one level/
opens from the outside in and closes from the inside out, so repeated
presses walk through the nest a level at a time.

| Key  | Does                                                |
|------+-----------------------------------------------------|
| =za= | toggle the fold at the cursor                       |
| =zA= | toggle it and everything nested in it               |
| =zo= | open one level at the cursor                        |
| =zO= | open every fold at the cursor                       |
| =zc= | close one level at the cursor                       |
| =zC= | close every fold at the cursor                      |
| =zv= | open just enough to see the line the cursor is on   |
| =zR= | open every fold in the buffer                       |
| =zM= | close every fold                                    |
| =zr= | one fold level less                                 |
| =zm= | one fold level more                                 |

Closing a fold the cursor is inside moves the cursor to that fold's
summary line, rather than leaving it on a hidden row.

Pause on =z= without typing a second key and a panel of every fold
command appears along the bottom of the window -- which-key, for the =z=
prefix. It is only a reminder: the keys still resolve immediately, so
typing =zc= at speed never puts it on screen and nothing it shows can
swallow a keystroke. In Visual mode it lists what Visual mode actually
has, which is =zf=.

=o= and =O= on a closed fold open the new line /outside/ it -- after the
last collapsed row, or before the first -- rather than dropping what you
type into the middle of a region you folded away.

** Making and unmaking them

| Key         | Does                                              |
|-------------+---------------------------------------------------|
| =zf=        | (Visual) fold the selected lines, closed          |
| =[count]zF= | fold =count= lines from the cursor down, closed   |
| =zd=        | delete the fold at the cursor                     |
| =zD=        | delete every fold at the cursor                   |
| =zE=        | delete every fold in the buffer                   |
| =zx=        | rebuild the computed folds now, and do =zv=       |

=zf= takes whichever lines the selection touches -- charwise or linewise,
it folds whole lines either way -- and needs at least two of them, as
does =zF=. A fold either of them makes is yours, not a provider's: none
of the recomputes below clear it, and it follows the text as you edit
around it.

=zd= and =zD= remove the fold itself, not just its collapsed state. One
that a provider owns can be rebuilt by that provider's next recompute --
the same caveat vim's own =zd= carries outside =foldmethod=manual=. =zE=
is the exception: it stops the automatic rebuild as well, so the buffer
stays unfolded until =zx= asks for the folds back.

** Turning folding off

| Key  | Does                                                    |
|------+---------------------------------------------------------|
| =zi= | folding off and on ('foldenable')                       |
| =zn= | off: every fold opens, and nothing collapses            |
| =zN= | on: every fold that was collapsed goes back as it was   |

Folding off opens everything without losing it -- =zN= (or =zi= again)
puts each fold back exactly as you left it. Any command that closes a
fold turns folding back on first, as in Vim.

** Moving between them

| Key  | Does                              |
|------+-----------------------------------|
| =zj= | to the start of the next fold     |
| =zk= | to the end of the previous fold   |

** What a folded line looks like

A closed fold keeps its own first line -- syntax highlighting and all --
rather than replacing it with a synthetic placeholder, and marks itself
four ways: a tinted band across the row, an accent rule down its left
edge, an accent =+= in the gutter, and =... N lines= after the text
saying how much is behind it. An open fold's start row shows a =-= in
the gutter. Clicking either marker toggles that fold without moving the
cursor.

The band and rule are derived from the theme's accent color, so a fold
reads the same way in every palette.

* Where folds come from

| Source                | For                                  |
|-----------------------+--------------------------------------|
| Treesitter            | code, via =:MepSyntaxFold=           |
| headline depth        | Org and Markdown                     |
| =\{\{\{= and =\}\}\}= | marker folds, in any filetype        |
| =zf= in Visual mode   | one you make by hand, any filetype   |

Org and marker folds are recomputed lazily -- right before a fold command
touches the buffer, rather than on every keystroke -- so they are always
current without costing anything while you type.

Org has its own cycling on =:MepOrgCycle=, which is the more natural way to
move through an outline.

* Folds across sessions

Folds are saved in the project session file, next to the layout, tabs and
cursor positions, and come back when the project is reopened.

| Kind                                   | Saved as                     |
|----------------------------------------+------------------------------|
| a fold you made (=zf= / =zF=)          | the fold itself              |
| a provider's fold you collapsed        | the collapse, not the fold   |
| a provider's fold left open            | nothing                      |

A provider's fold (an Org headline, a =\{\{\{= marker, a treesitter
block) is rebuilt from the text next time anyway, so there is nothing
worth saving but the fact that you had closed it -- which comes back
matched by start row, the same way a recompute preserves it inside a
session. A fold you made by hand exists nowhere but in mep, so it is
saved whole.

Two things to know:

- Folds come back whether or not a layout does. Opening a project (from
  the dashboard, or =mep --project <path>=) restores its whole saved
  layout; a bare =mep file.txt= restores no layout at all, by design --
  but it still finds that file folded the way you left it, because a
  fold belongs to the buffer rather than to the pane.
- A saved range that no longer fits the file (it was edited elsewhere in
  between, or shrank) is dropped rather than applied to the wrong lines.

* From Lua

#+begin_src lua
mep.fold_create(start_row, end_row)
mep.fold_toggle(row)
mep.fold_clear_provider()
#+end_src

A feature that computes its own folds registers them with =fold_create= and
clears its previous set with =fold_clear_provider=.
