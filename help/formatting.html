Formatting

Formatting a buffer

gf, or :MepFormat. It formats the buffer's current text, including unsaved changes -- it never needs the file written first and never formats a stale copy from disk.

That is a deliberately short table. Most languages already have a formatter behind their language server, so the table only carries the cases where a dedicated tool is clearly better.

C, C++, Python, R, Maxima, shell scripts, Clojure, Common Lisp, Crystal and C# need nothing installed at all: all ten formatters are built into mep, so gf on a .c, .cpp, .h, .py, .R, .mac, .sh, .clj, .lisp, .cr or .cs buffer works on a machine with no clang-format, no black, no air, no shfmt, no cljfmt, no Emacs and no Python, R, Maxima, JVM, Lisp, Crystal or .NET toolchain, and answers instantly because nothing is spawned.

Org code blocks

In an .org file gf formats code, never the prose around it.

Where the cursor isWhat gf does
inside a #+begin_src blockformats that block's body
anywhere elseformats every block that has a formatter

:MepOrgFormatBlock and :MepOrgFormatBlocks are the same two, by name.

The block's language picks the formatter -- #+begin_src python gets the built-in Python formatter and #+begin_src cpp the built-in C++ one, the same as a .py or .cpp file, because the block's language name is translated through its babel file extension before the table above is looked up.

A block indented under a heading is dedented before the formatter sees it and re-indented after, so the org file's own layout survives. A body whose lines do not share one indent (tabs on some, spaces on others) is passed through exactly as written.

For a language with no entry in the table, a single-block gf falls back to that block's own language server -- the one already answering hover and completion inside the block. The whole-file sweep does not: it only runs the table, and reports those blocks as skipped.

The C++ formatter

C++ is formatted by mep itself. Nothing is spawned, no clang-format has to be on PATH, and gf works the same in a fresh checkout as on a fully set-up machine. The same formatter handles .cpp, .cc, .cxx, .h, .hpp, .hh, .hxx, .ipp, .inl, .cu and .cuh.

It is shaped after clang-format, in the dialect mep's own source is written in: 4-space indents, Type *name with the star on the name, =if (x)= with a space and foo(x) without, namespace bodies not indented, access specifiers flush with the class, case labels a level inside the switch, continuation lines aligned under the open bracket and packed, runs of trailing // comments lined up in one column with two spaces in front of them, and a 100-column margin.

cpp Copy
struct Point{int x=0;int y=0;};
int Sum(const std::vector<Point>&pts,int scale){
int total=0;
for(size_t i=0;i<pts.size();i++)total+=pts[i].x*scale+pts[i].y;
return total;
}

becomes

cpp Copy
struct Point { int x = 0; int y = 0; };
int Sum(const std::vector<Point> &pts, int scale) {
    int total = 0;
    for (size_t i = 0; i < pts.size(); i++) total += pts[i].x * scale + pts[i].y;
    return total;
}

A braced initializer whose last element carries a comma stays exploded, one element per line, however short it would be -- the same "magic trailing comma" black has and clang-format reads the same way. Remove the comma and it collapses back onto one line:

cpp Copy
int a[] = {1, 2, 3,};   // stays one per line
int b[] = {1, 2, 3};    // stays on one line

It is not clang-format, though, and the differences are deliberate:

  • Short forms are preserved, not imposed. if (c) return; and =int f() { return 1; }= stay on one line if that is how they were written and they fit. Nothing is ever joined onto one line that the input had apart, so the mixed style real C++ is written in survives instead of being flattened one way or the other.
  • Preprocessor directives are re-spaced but never re-wrapped. A #define carrying a backslash continuation is emitted byte for byte, and the code inside a macro body is not formatted -- without expanding it there is no way to know whether it is a statement, an expression or a fragment of either. Directives go flush left, including inside a function body.
  • Greedy, not optimal, line breaking. clang-format will take a worse break early to get a better one later; this takes the first split that fits. Long chained calls in particular wrap less prettily.
  • No comment reflowing. A too-long // stays too long, and a block comment's interior is only re-indented when every line of it starts with a single *. A banner drawn with **, ASCII art or commented-out code is left byte for byte.
  • No #include sorting, and nothing is ever inserted or rewritten that was not already there -- no braces, no const, no blank lines, and in particular no fixing up of a \} // namespace foo comment, which clang-format does and which edits the code's text rather than its layout.
  • A macro invocation with no semicolon (ABSL_NAMESPACE_BEGIN) reads as part of the declaration after it, because in a token stream that is exactly what it looks like.

It will not rewrite code it cannot prove it preserved

A C++ formatter only ever moves whitespace, so the proof-reading is exact: every result is re-lexed and compared against the original token for token, spelling for spelling, with no tolerance at all except trailing whitespace inside a comment. If that check fails -- or the file does not lex in the first place -- gf reports the reason and *leaves the buffer exactly as it was*, naming the line so the cursor can be put on it.

That check is also what licenses the guessing C++ forces on a formatter that does not parse. Whether a < opens a template or compares two numbers, whether a * declares a pointer or multiplies, whether a { opens a block or an initializer list -- none of those can be settled without name lookup over the whole translation unit. Guessing wrong moves a space; it cannot move a token, and the check proves it.

There is exactly one place in C++ where the whitespace between two tokens is meaningful rather than cosmetic, and the check above is blind to it because the token streams really are identical: #define X(a) defines a function-like macro and #define X (a) an object-like one. That single space is carried over from the source rather than re-derived.

That is what makes the guesses C++ forces on a formatter safe. The C formatter

C files are laid out exactly the way clang-format lays them out in its default LLVM style, by mep itself -- no clang-format binary, no libclang. It is a port of clang-format's own pipeline, cut down to C: the same lexer, the same parser into lines, the same token annotation, the same penalty-based search for where to break a long line, the same whitespace pass. It is also what mep's C language server formats with.

c Copy
#include <stdio.h>
struct point{int x;int y;};
static int sum(const struct point*pts,int n,int scale){
int total=0;
for(int i=0;i<n;i++)total+=pts[i].x*scale+pts[i].y;
switch(scale){case 0:return 0;default:break;}
return total;}
#define SQUARE(x) ((x)*(x)) // squares x

becomes

c Copy
#include <stdio.h>
struct point {
  int x;
  int y;
};
static int sum(const struct point *pts, int n, int scale) {
  int total = 0;
  for (int i = 0; i < n; i++)
    total += pts[i].x * scale + pts[i].y;
  switch (scale) {
  case 0:
    return 0;
  default:
    break;
  }
  return total;
}
#define SQUARE(x) ((x) * (x)) // squares x

Two-space indents, an 80-column margin, int *p with the star on the name, braces on the line that opens them, case labels at the switch's own indent, a short function kept on one line, continuation lines aligned after the open bracket, runs of trailing comments lined up, the backslashes of a multi-line #define lined up at the margin, comments that run past it reflowed and long strings split. Every #if / #else branch is laid out, not just the first.

On the 841 C files of mep's corpus that clang-format finishes (Lua, CPython, SQLite's shell, tree-sitter), every one comes out byte-identical to clang-format --style"\{BasedOnStyle: LLVM, SortIncludes: Never\}"= -- about 700,000 lines. The one difference by design:

  • =#include= lines are never reordered. LLVM style sorts them within each block; in C the order of includes can matter.

Like clang-format, a handful of files only settle on a second gf (8 of the 841 -- the same 8 for both, with the same second result).

It will not rewrite code it cannot prove it preserved

The result is lexed again and compared with the input token for token: only whitespace may differ, plus what reflowing a comment or splitting a string changes -- the words of every comment and the bytes of every string stay the same, in order -- and no token may move into or out of a preprocessor directive. A #define's name keeps its ( attached or detached, since that space decides whether the macro takes arguments. If the check fails, gf leaves the buffer exactly as it was and names the line.

Each combination of #if branches is a pass over the whole file, so a file with very many of them costs that many passes. clang-format has the same cost and no limit: on SQLite's 9 MB amalgamation (sqlite3.c) it runs for minutes and takes tens of gigabytes. mep counts the combinations on the first pass and refuses up front, with a message, when the file is too large for them; anything up to about a megabyte with a hundred-odd combinations (SQLite's shell.c) is still formatted.

The Python formatter

Python is formatted by mep itself. Nothing is spawned, nothing has to be on PATH, and gf works the same in a fresh checkout as on a fully set-up machine.

It is shaped after black, because that is what a Python buffer is expected to look like: 4-space indents, double quotes, 88-column lines, one argument per line with a trailing comma once a call has to be exploded, two blank lines around top-level def and class.

It is not black, though, and the differences are deliberate:

  • No invented parentheses. black wraps a too-long return a and b in parentheses of its own so it can split it. mep's does not, so a long line with no bracket in it stays long rather than being restructured.
  • =match= statements are left alone. match and case are ordinary identifiers until they are not, and telling the two apart needs a real parser.
  • Comments are normalized, not moved. They keep the token they follow.

Indentation alone, on every save

gf is the whole formatter. The much smaller half of it -- put the indentation back on the four-space grid and change nothing else -- runs on its own every time you save a Python buffer, which is what fixes a block pasted from a two-space or tab-indented source. It is :set pyindent (on by default; see Options), it shares this formatter's tokenizer and its proof-reading, and it leaves a file it cannot read unambiguously completely alone.

It will not rewrite code it cannot prove it preserved

Every result is proof-read before it reaches the buffer: the formatted text is re-tokenized and compared against the original, allowing only the changes the formatter is entitled to make (whitespace, quote style, numeric literal case, and the trailing commas an exploded bracket gains).

If that check fails -- or the file does not parse in the first place -- gf reports the reason and leaves the buffer exactly as it was. A syntax error names its line, so the cursor can be put on it.

Options

lua Copy
mep.format_languages.py.width = 100   -- default 88

To go back to black instead, replace the entry with an ordinary argv one:

lua Copy

The Maxima formatter

Maxima has no formatter of its own to defer to -- its grind is a printer for values, and running a file through it would lose the file's comments and its $ terminators. So mep's own follows the style grind prints in where that style is also what real Maxima is written in, measured against the 657 .mac files Maxima's distribution ships:

WrittenBecause
f(x)a call's parenthesis is tight (113,051 files to 22,752)
a+b, u^2arithmetic is dense (18,040 to 3,378)
a > 0, p and qcomparisons and logic are spaced
x : 1, f(u) : u^2=assignment and definition are spaced
f(a, b)a comma is followed by a space

The rule behind the last two is *structure is spaced, arithmetic is dense*, so a : x+y shows at a glance which part is the assignment and which is the sum.

maxima Copy
f(x,y):=block([a:1,b],a:x+y,if a>0 then b:a else b:-a,return(b))$

becomes

maxima Copy
f(x, y) := block([a : 1, b],
  a : x+y,
  if a > 0 then b : a else b : -a,
  return(b))$

A block keeps its local list on the opening line and puts one statement per line under it. A list packs to the margin instead, because a list is usually data. A long conditional breaks before then and else.

Three things are never touched, because in Maxima they are meaning rather than layout: a statement's terminator (; displays the result, $ does not), a string's escapes, and the spelling of a loop clause (for i : 1 and for i from 1 are the same loop, and each is left as it was written).

The Bash formatter

Shell scripts are laid out the way shfmt lays them out, by mep itself: the same parser mep's Bash language server uses reads the script, and the tree is printed back.

sh Copy
greet () {
  local name=$1
    if [ -n "$name" ]
    then
  echo "hi $name";
  fi
}
for x in a b;do greet $x;done

becomes

sh Copy
greet() {
  local name=$1
  if [ -n "$name" ]; then
    echo "hi $name"
  fi
}
for x in a b; do greet $x; done
  • then and do go on the line that opens the block, one statement per line inside it; a block written on one line with a single statement in each body ([[ -f x ]] || { echo no; exit 1; } has two, so it opens up) stays on one line.
  • Single spaces between words and around |, && and ;;; name(); redirections tight to their target (>file, 2>&1), and moved after the arguments unless written right after the command name, as shfmt does.
  • Arithmetic re-spaced: $((a + 1)), ((i++)), for ((i = 0; i < n; i++)).
  • Backquotes become $(...).
  • A line broken after &&, || or |, or with a backslash inside a command, stays broken there, one level in.
  • Comments stay where they are, a run of trailing comments is lined up, and at most one blank line is kept between statements.
  • Here-document bodies are kept byte for byte (a <<- body, whose leading tabs bash strips, is re-indented when the file indents with tabs).

The indent unit is the file's own -- tabs, or the width of spaces its blocks are indented by -- and so is whether case patterns sit a level inside the case. A file with nothing indented yet gets tabs.

On the 3,432 scripts of mep's Bash test corpus (bash-completion, git's test suite, bash's examples and tests, every .sh in nixpkgs), with tabs, 96% of files come out byte-identical to shfmt's output and 99.9% of lines. The rest are deliberate:

  • Array subscripts are left as written. shfmt re-spaces a[i+1] as arithmetic, which for an associative array changes the key: [x86_64-linux] becomes [x86_64 - linux]. nixpkgs has update scripts that shfmt breaks that way.
  • =${x/pat}= is not rewritten to ${x/pat/}, and nothing inside ${...} is re-spaced.
  • Here-document bodies are not formatted, not even the $(...) in them.
  • *Backquotes holding nested backquotes, or written right after a $, stay backquotes.*

It will not rewrite a script it cannot prove it preserved

The result is parsed again and compared with the original, command by command and word by word, comments and here-document bodies included; only the layout may differ. A script that does not parse, or a layout that would change anything else, leaves the buffer exactly as it was and says why -- with the line, for a syntax error.

The Clojure formatter

Clojure files are laid out the way cljfmt lays them out with its default options, by mep itself -- no JVM, no cljfmt binary. It also runs for .cljs, .cljc, .cljd, .edn and .bb files, and is what mep's Clojure language server formats with.

clojure Copy
(defn greet [name]
(let [msg (str "hi " name)
]
( println msg )
))

becomes

clojure Copy
(defn greet [name]
  (let [msg (str "hi " name)]
    (println msg)))
  • Indentation is recomputed from the forms: a call's arguments line up under its first argument (or sit one column in when none is on the head's line); the body of defn, let, when, fn, cond->, deftype... sits two columns in, as cljfmt's indentation table says, and so does that of any def... or with-... form; a collection's elements line up under its first. Top-level forms start at column 0.
  • No space just inside brackets -- ( foo ) is (foo) -- and a closing bracket left alone on its line joins the line before it.
  • One space between forms that touch, (foo(bar)) becoming (foo (bar)).
  • No trailing whitespace; runs of blank lines become one.

Like cljfmt, it never breaks or joins lines otherwise, never touches the text of a string or a comment, and leaves a line that starts with a comment where it is. It does not wrap, so it has no width.

On the 1,772 files of mep's Clojure corpus that read (Clojure's and ClojureScript's own source, clj-kondo, clojure-lsp, babashka, rewrite-clj...), 97% come out byte-identical to cljfmt's output and 99.95% of lines. The rest are cljfmt's own corners -- the indentation of some forms inside #?(...) reader conditionals and syntax-quoted templates, lines holding nothing but commas.

It will not rewrite a file it cannot prove it preserved

The result is read again and its tokens compared with the input's; only whitespace may differ. A file that does not read (an unclosed paren, an odd map) leaves the buffer exactly as it was, and gf says why, with the line.

The Common Lisp formatter

Common Lisp has no cljfmt or black; the layout every Lisp programmer's tools agree on is Emacs's -- lisp-mode with common-lisp-indent-function, what SLIME and Sly set up. mep computes that indentation itself, rule for rule, with no Emacs and no Lisp image. It runs for .lisp, .lsp, .cl and .asd files, the Enter key's auto-indent in those buffers uses the same rules, and it is what mep's Common Lisp language server formats with.

lisp Copy
(defun greet (name)
(let ((msg (format nil "hi ~a" name)))
  ( print msg )
    )
)
(defmacro with-thing ((var) &body body)
`(let ((,var 1))
,@body))

becomes

lisp Copy
(defun greet (name)
  (let ((msg (format nil "hi ~a" name)))
    (print msg)))
(defmacro with-thing ((var) &body body)
  `(let ((,var 1))
     ,@body))
  • Indentation as common-lisp-indent-function computes it: the specs of defun, let, flet, case, destructuring-bind, handler-case, loop, tagbody, do...; any def... form indented like defun and any with-... or do-... form like a body form; package prefixes ignored; a call's arguments under the first one, a quoted list's elements under its first, a keyword under the keyword above it.
  • No space just inside parens -- ( foo ) is (foo) -- and a close paren alone on its line joins the line before, unless that line ends in a ; comment or the paren carries a comment of its own.
  • No trailing whitespace, at most two blank lines in a row, a final newline and no blank lines after it; indentation is spaces.

The text of strings, |...| symbols, comments, character literals such as #\( and #+feature expressions is never touched, and lines are never broken or joined otherwise. It does not wrap, so it has no width.

On the 1,521 files of mep's Common Lisp corpus (SBCL and the libraries packaged with it) that Emacs indents, 1,519 come out byte-identical to Emacs's indent-region with the same whitespace rules -- every line of 701,176 -- and each is a fixed point. Where it differs from Emacs, on purpose: a line inside a #|...|# comment keeps its indentation (Emacs re-indents a block comment as code); a line holding only a single-=;= comment keeps its column (Emacs sends it to column 40); and a defmethod's qualifiers are counted from the form itself, where Emacs, on a file not yet indented, can find the wrong enclosing form and indent the body as the lambda list.

It will not rewrite a file it cannot prove it preserved

The result is read again and its tokens compared with the input's; only whitespace may differ. A file that does not read -- an unclosed paren or string -- leaves the buffer exactly as it was, and gf says why, with the line.

Options

Your own macros indent as calls until told otherwise. indent adds or replaces specs, keyed by the operator's lower-case name without a package: a number of distinguished arguments before a body, a cl-indent list, or the name of an operator to indent like.

lua Copy

  ['with-connection'] = '1',          -- (with-connection (c db) body...)
  ['define-route'] = 'defun',
  ['my-case'] = 'case',
  ['do-rows'] = '(4 &body)',
}

The Crystal formatter

Crystal has one layout -- crystal tool format's, which takes no options -- and mep produces it itself, with no crystal binary: the formatter is a port of the compiler's own (formatter.cr, Crystal 1.19), running on mep's port of the compiler's lexer and parser. It is also what mep's Crystal language server formats with.

crystal Copy
class Greeter
def initialize(@name : String)
end
def greet( times=1 )
times.times{|i| puts "hi #{@name}" }
end
end

becomes

crystal Copy
class Greeter
  def initialize(@name : String)
  end

  def greet(times = 1)
    times.times { |i| puts "hi #{@name}" }
  end
end

Everything crystal tool format does, it does: two-space indentation, spacing around operators, =,= and block braces, one blank line between definitions, when ... then rows, => columns in a hash literal and trailing comments lined up, heredoc bodies moved with their start, the ```crystal examples inside doc comments formatted too, and macro bodies formatted where the code between the tags is Crystal on its own.

All 1,128 single-line cases of the compiler's formatter spec give the compiler's answer. On mep's Crystal corpus (4,602 files: the compiler and standard library, crystalline, ameba, invidious, mint, shards and the other Crystal projects nixpkgs packages), every file comes out byte-identical to crystal tool format, and so do 4,454 of 4,456 copies with their indentation and spacing scrambled; formatting twice changes nothing.

The one difference is deliberate: a string literal that spans lines keeps the trailing spaces of its lines. They are part of the string's value, and crystal tool format strips them anyway, which changes the program.

It will not rewrite a file it cannot prove it preserved

The result is parsed again and its tree compared with the input's, node for node, and its comments with the input's, in order. A file that does not parse leaves the buffer as it was, and gf gives the compiler's own syntax error, worded the same, with its line.

Using crystal tool format instead

lua Copy
mep.format_languages.cr = {'crystal', 'tool', 'format', '-'}

The C# formatter

mep lays C# out the way dotnet format whitespace does with no .editorconfig -- four-space indentation, braces on their own lines, its spacing rules -- and it does so itself, with no .NET: the formatter is a port of Roslyn's own formatting engine (the C# formatting rules and the engine that applies them, at the commit the .NET 10 SDK's dotnet format was built from), running on mep's port of Roslyn's parser, whose trees are Roslyn's own. It is also what mep's C# language server formats with.

csharp Copy
namespace Shapes{
public class Polygon {
  int sides=3;
public  int Sides{get{return sides;}set{sides=value;}}
public double Angle( ){
if(sides<3){throw new System.ArgumentException("too few sides");}
    return 180.0*(sides-2)/sides;
    }
}
}

becomes

csharp Copy
namespace Shapes
{
    public class Polygon
    {
        int sides = 3;
        public int Sides { get { return sides; } set { sides = value; } }
        public double Angle()
        {
            if (sides < 3) { throw new System.ArgumentException("too few sides"); }
            return 180.0 * (sides - 2) / sides;
        }
    }
}

Like Roslyn's, it fixes whitespace and indentation and nothing else: it moves braces of types, members and blocks onto their own lines, but keeps a block, property or statement the author wrote on one line on one line; it spaces operators, commas, casts and keywords, indents blocks, switch sections, embedded statements, lambdas, initializers, collection expressions, patterns and query clauses, re-indents comments, doc comments and #region lines with the code, puts other directives at column 0, and leaves #pragma warning disable format regions alone. It never joins or breaks lines to fit a width, and it keeps the user's own indentation of a continued argument or expression.

All 324 of Roslyn's own formatting tests that are a plain input and expected text (AssertFormatAsync, default options) give Roslyn's answer. On mep's C# corpus (17,828 files: Roslyn's compilers, analyzers and tests, jellyfin, osu!, OpenRA, Pinta, ILSpy, ArchiSteamFarm, OmniSharp and more), every file comes out byte-identical to dotnet format whitespace but one, and so do all 17,828 copies with their indentation and spacing scrambled. Formatting twice changes nothing on every file of the corpus; on 613 of the scrambled copies a second pass moves a continued argument's contents again -- exactly as Roslyn's own second pass does.

Like dotnet format, a file with syntax errors is still formatted (the space next to a missing token is left as it is), and a byte-order mark is kept. The one difference is deliberate: a file that is not valid UTF-8 is refused -- dotnet format reads it with replacement characters and writes them back, losing the original bytes (the one corpus file is Shift-JIS).

It will not rewrite a file it cannot prove it preserved

The result is parsed again and compared with the input's tree: every node and token, the same syntax errors, the same comments and directives up to whitespace. If anything else differs, the buffer is left as it was and gf says where.

Options

lua Copy
mep.format_languages.cs.indent = 2      -- indent_size, default 4
mep.format_languages.cs.tabs = true     -- indent_style = tab (indent columns wide)

These are dotnet format's indent_size and indent_style; with them set the output still matches dotnet format given the same .editorconfig. The other Roslyn options (csharp_new_line_before_open_brace and the rest) are at their defaults: a project's .editorconfig is not read.

Using dotnet format instead

dotnet format formats files in a folder rather than a stream, so it runs in file mode on a copy:

lua Copy
mep.format_languages.cs = {'sh', '-c',
  'd=${XDG_CACHE_HOME:-$HOME/.cache}/mep/dotnet-format && mkdir -p "$d" && '
    .. 'cp "$1" "$d/buffer.cs" && dotnet format whitespace --folder "$d" --include buffer.cs && '
    .. 'cp "$d/buffer.cs" "$1"',
  'sh', '{}', mode = 'file'}

An .editorconfig in that directory is what it reads its options from.

The R formatter

mep's R formatter follows the tidyverse style: two-space indent, spaces around binary operators (but not around ^, :, ::, $ or @), <- for assignment, double-quoted strings, and an 80-column margin that calls, argument lists and pipelines are broken across to respect.

r Copy
result=some_function(argument_one=1,argument_two=2,argument_three='three')

becomes

r Copy
result <- some_function(
  argument_one = 1,
  argument_two = 2,
  argument_three = "three"
)

A trailing block "hugs" the call it belongs to rather than exploding the argument list, which is the shape R is actually written in:

r Copy
test_that("it works", {
  expect_equal(1, 1)
})

Two things it deliberately does not do: it never adds braces to an if=/=for body that has none, and it never rewrites a %>% into a |>. Both change the code rather than its layout, which is not what gf is for.

Comments are kept where they were written -- above a statement, after it, or after the operator they follow -- and one blank line between statements survives (several collapse to one).

A file it cannot parse is left completely alone: gf reports the line the parse failed on and the buffer is untouched. So is a file where the formatter's own check -- it re-reads its output and compares it, token for token, against the input -- finds a difference it did not intend.

Changing the width

lua Copy
mep.format_languages.R.width = 100

Using air or styler instead

lua Copy
-- Posit's air, the tidyverse formatter this style follows:
mep.format_languages.R = {'air', 'format', '--stdin-file-path={}'}
-- or styler, which rewrites a file in place rather than filtering:
mep.format_languages.R = {mode = 'file', 'Rscript', '-e',
  'styler::style_file(commandArgs(TRUE))', '{}'}

Both need the tool installed, and air takes its own margin from the nearest air.toml rather than from width above.

Line width

The built-in formatters wrap at 100 columns for C++, 88 for Python and 80 for C and R -- width in each one's table entry, and the subsections above change it. The Bash one does not wrap: like shfmt, it keeps a script's own line breaks, and so do the Clojure, Common Lisp, Crystal and C# ones. clang-format, if you put it back for C or C++, takes its margin from the project's own .clang-format instead.

Adding one

lua Copy
mep.format_languages.js = {'prettier', '--stdin-filepath', '{}'}
mep.format_languages.ts = mep.format_languages.js

The entry is an argv array. \{\} anywhere in it is replaced by a path.

Three modes:

  • filter (the default): the buffer is written to the formatter's stdin and its stdout replaces the buffer. \{\} is the buffer's real absolute filename.
  • file: add mode = 'file'=, and =\{\} is a temporary file the formatter edits in place.
  • builtin: no program at all -- =\{builtin = 'format_python', name = '...', width = 88\}= names a mep.* function taking the text and a width and returning the formatted text, which runs in-process. This is how every built-in entry above is wired.

Entries are looked up by bare extension, so every extension of a language needs its own key -- which is why the built-in table aliases .h, .cc, .hpp and the rest onto the C++ entry.

Why the placeholder matters

A formatter reading stdin has no idea what file it is looking at. clang-format and air have to be told -- --assume-filename and --stdin-file-path -- or they cannot find the .clang-format or air.toml the project configures them with, and they silently format to their own defaults instead. (A builtin entry has no such problem: it is handed the text directly and takes its options from its own table entry.)

So a filter-mode entry should almost always pass \{\} somewhere.
