Formatting

Formatting a buffer

gf, or :MepFormat. It formats the buffer's current text, including unsaved changes -- it never needs the file written first and never formats a stale copy from disk.

What runs

FiletypeFormatter
C, C++ and friendsclang-format
Pythonbuilt in -- mep's own, nothing to install
Rbuilt in -- mep's own, nothing to install
anything elsemep.lsp_format, if a server is attached

That is a deliberately short table. Most languages already have a formatter behind their language server, so the table only carries the cases where a dedicated tool is clearly better.

Python and R need nothing installed at all: both formatters are built into mep, so gf on a .py or .R buffer works on a machine with no black, no air and no Python or R toolchain, and answers instantly because nothing is spawned.

Org code blocks

In an .org file gf formats code, never the prose around it.

Where the cursor isWhat gf does
inside a #+begin_src blockformats that block's body
anywhere elseformats every block that has a formatter

:MepOrgFormatBlock and :MepOrgFormatBlocks are the same two, by name.

The block's language picks the formatter -- #+begin_src python gets the built-in Python formatter, the same as a .py file, because the block's language name is translated through its babel file extension before the table above is looked up.

A block indented under a heading is dedented before the formatter sees it and re-indented after, so the org file's own layout survives. A body whose lines do not share one indent (tabs on some, spaces on others) is passed through exactly as written.

For a language with no entry in the table, a single-block gf falls back to that block's own language server -- the one already answering hover and completion inside the block. The whole-file sweep does not: it only runs the table, and reports those blocks as skipped.

The Python formatter

Python is formatted by mep itself. Nothing is spawned, nothing has to be on PATH, and gf works the same in a fresh checkout as on a fully set-up machine.

It is shaped after black, because that is what a Python buffer is expected to look like: 4-space indents, double quotes, 88-column lines, one argument per line with a trailing comma once a call has to be exploded, two blank lines around top-level def and class.

It is not black, though, and the differences are deliberate:

  • No invented parentheses. black wraps a too-long return a and b in parentheses of its own so it can split it. mep's does not, so a long line with no bracket in it stays long rather than being restructured.
  • =match= statements are left alone. match and case are ordinary identifiers until they are not, and telling the two apart needs a real parser.
  • Comments are normalized, not moved. They keep the token they follow.

It will not rewrite code it cannot prove it preserved

Every result is proof-read before it reaches the buffer: the formatted text is re-tokenized and compared against the original, allowing only the changes the formatter is entitled to make (whitespace, quote style, numeric literal case, and the trailing commas an exploded bracket gains).

If that check fails -- or the file does not parse in the first place -- gf reports the reason and leaves the buffer exactly as it was. A syntax error names its line, so the cursor can be put on it.

Options

lua Copy
mep.format_languages.py.width = 100   -- default 88

To go back to black instead, replace the entry with an ordinary argv one:

lua Copy
mep.format_languages.py = {'black', '--quiet', '--stdin-filename={}', '-'}

The R formatter

mep's R formatter follows the tidyverse style: two-space indent, spaces around binary operators (but not around ^, :, ::, $ or @), <- for assignment, double-quoted strings, and an 80-column margin that calls, argument lists and pipelines are broken across to respect.

r Copy
result=some_function(argument_one=1,argument_two=2,argument_three='three')

becomes

r Copy
result <- some_function(
  argument_one = 1,
  argument_two = 2,
  argument_three = "three"
)

A trailing block "hugs" the call it belongs to rather than exploding the argument list, which is the shape R is actually written in:

r Copy
test_that("it works", {
  expect_equal(1, 1)
})

Two things it deliberately does not do: it never adds braces to an if=/=for body that has none, and it never rewrites a %>% into a |>. Both change the code rather than its layout, which is not what gf is for.

Comments are kept where they were written -- above a statement, after it, or after the operator they follow -- and one blank line between statements survives (several collapse to one).

A file it cannot parse is left completely alone: gf reports the line the parse failed on and the buffer is untouched. So is a file where the formatter's own check -- it re-reads its output and compares it, token for token, against the input -- finds a difference it did not intend.

Changing the width

lua Copy
mep.format_languages.R.width = 100

Using air or styler instead

lua Copy
-- Posit's air, the tidyverse formatter this style follows:
mep.format_languages.R = {'air', 'format', '--stdin-file-path={}'}
-- or styler, which rewrites a file in place rather than filtering:
mep.format_languages.R = {mode = 'file', 'Rscript', '-e',
  'styler::style_file(commandArgs(TRUE))', '{}'}

Both need the tool installed, and air takes its own margin from the nearest air.toml rather than from width above.

Line width

The built-in formatters wrap at 88 columns for Python and 80 for R -- width in each one's table entry, and the two subsections above change it. clang-format takes its margin from the project's own .clang-format instead.

Adding one

lua Copy
mep.format_languages.js = {'prettier', '--stdin-filepath', '{}'}
mep.format_languages.ts = mep.format_languages.js

The entry is an argv array. \{\} anywhere in it is replaced by a path.

Three modes:

  • filter (the default): the buffer is written to the formatter's stdin and its stdout replaces the buffer. \{\} is the buffer's real absolute filename.
  • file: add mode = 'file'=, and =\{\} is a temporary file the formatter edits in place.
  • builtin: no program at all -- =\{builtin = 'format_python', name = '...', width = 88\}= names a mep.* function taking the text and a width and returning the formatted text, which runs in-process. This is how both the Python and the R entries are wired.

Entries are looked up by bare extension, so every extension of a language needs its own key -- which is why the built-in table aliases .h, .cc, .hpp and the rest onto the C entry.

Why the placeholder matters

A formatter reading stdin has no idea what file it is looking at. clang-format and air have to be told -- --assume-filename and --stdin-file-path -- or they cannot find the .clang-format or air.toml the project configures them with, and they silently format to their own defaults instead. (A builtin entry has no such problem: it is handed the text directly and takes its options from its own table entry.)

So a filter-mode entry should almost always pass \{\} somewhere.
