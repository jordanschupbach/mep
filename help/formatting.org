* Formatting a buffer

=gf=, or =:MepFormat=. It formats the buffer's *current text*, including
unsaved changes -- it never needs the file written first and never formats a
stale copy from disk.

That is a deliberately short table. Most languages already have a formatter
behind their language server, so the table only carries the cases where a
dedicated tool is clearly better.

C, C++, Python, R, Maxima, shell scripts, Clojure, Common Lisp, Crystal,
C#, SQL, Nix, Lua and JavaScript/TypeScript need nothing installed at all: all fourteen
formatters are built into mep, so =gf= on a =.c=, =.cpp=, =.h=, =.py=, =.R=,
=.mac=, =.sh=, =.clj=, =.lisp=, =.cr=, =.cs=, =.sql=, =.nix=, =.lua=, =.js= or =.ts=
buffer works on a machine with no =clang-format=, no =black=, no =air=, no
=shfmt=, no =cljfmt=, no =sqlfluff=, no =nixfmt=, no =stylua=, no =prettier=,
no Node, no Emacs and no Python, R, Maxima, JVM, Lisp, Crystal, .NET or
Haskell toolchain, and answers instantly because nothing is spawned.

* Org code blocks

In an =.org= file =gf= formats *code*, never the prose around it.

| Where the cursor is        | What =gf= does                          |
|----------------------------+-----------------------------------------|
| inside a =#+begin_src= block | formats that block's body             |
| anywhere else              | formats every block that has a formatter |

=:MepOrgFormatBlock= and =:MepOrgFormatBlocks= are the same two, by name.

The block's language picks the formatter -- =#+begin_src python= gets the
built-in Python formatter and =#+begin_src cpp= the built-in C++ one, the
same as a =.py= or =.cpp= file, because the block's language name is
translated through its babel file extension before the table above is looked
up.

A block indented under a heading is dedented before the formatter sees it
and re-indented after, so the org file's own layout survives. A body whose
lines do not share one indent (tabs on some, spaces on others) is passed
through exactly as written.

For a language with *no* entry in the table, a single-block =gf= falls back
to that block's own language server -- the one already answering
[[file:org-polyglot.html][hover and completion inside the block]]. The
whole-file sweep does not: it only runs the table, and reports those blocks
as skipped.

* mepml documents

In a =.mepml= file =gf= formats the prose /and/ the code.

| Where the cursor is              | What =gf= does                                   |
|----------------------------------+--------------------------------------------------|
| on a code block's fences or body | formats that block with its language's formatter |
| anywhere else                    | formats the document, then every code block      |

=:MepmlFormatBlock= and =:MepmlFormat= are the same two, by name. A code
block works as in an org file (above), with one difference: it is wrapped at
the document's width -- =:set textwidth=, 80 by default -- rather than at
the language's own (88 for Python, 100 for C++), since it sits on the same
page as the prose.

The document itself goes through mep's mepml formatter:

- paragraphs, list items and the =\abstract='s paragraphs are refilled to
  =:set textwidth= columns, a list item's later lines hanging under its text;
- table columns are padded so the pipes line up, the separator row sized to
  match, alignment colons kept and each cell aligned the way they say;
- a comment or callout with a line past the width is refilled (one that
  fits is left as you wrote it);
- trailing whitespace goes, runs of blank lines become one, and blank lines
  at the top and bottom of the file go.

It leaves alone what is not prose: code blocks and their results (a
=results=markdown= region is a program's output, even though it reads as
blocks), display maths, =\define=, =\raw= and command blocks, HTML and SVG
markup, and headings.

A line is never broken inside maths, =`verbatim`=, a link, a citation or a
command's arguments, and never so that the next line starts with something
that reads as another block -- =- =, =1.=, =>= or =//= at the start of a
line would make a list item, a heading or a comment. The word before such a
piece goes down with it instead. An inline =// remark= stays at the end of
its line.

** It will not change what the document says

After formatting, the result is parsed again and compared with the
original: the same blocks, the same text and markup, the same options,
whitespace aside. A change that fails the check is left out, and =gf= says
how many were. So formatting can make the file tidier, never different.

To pin a width for mepml alone:

#+begin_src lua
mep.format_languages.mepml.width = 72
#+end_src

* The C++ formatter

C++ is formatted by mep itself. Nothing is spawned, no =clang-format= has to
be on =PATH=, and =gf= works the same in a fresh checkout as on a fully
set-up machine. The same formatter handles =.cpp=, =.cc=, =.cxx=, =.h=,
=.hpp=, =.hh=, =.hxx=, =.ipp=, =.inl=, =.cu= and =.cuh=.

It is shaped after =clang-format=, in the dialect mep's own source is
written in: 4-space indents, =Type *name= with the star on the name, =if
(x)= with a space and =foo(x)= without, namespace bodies not indented,
access specifiers flush with the class, =case= labels a level inside the
=switch=, continuation lines aligned under the open bracket and packed, runs
of trailing =//= comments lined up in one column with two spaces in front of
them, and a 100-column margin.

#+begin_src cpp
struct Point{int x=0;int y=0;};
int Sum(const std::vector<Point>&pts,int scale){
int total=0;
for(size_t i=0;i<pts.size();i++)total+=pts[i].x*scale+pts[i].y;
return total;
}
#+end_src

becomes

#+begin_src cpp
struct Point { int x = 0; int y = 0; };
int Sum(const std::vector<Point> &pts, int scale) {
    int total = 0;
    for (size_t i = 0; i < pts.size(); i++) total += pts[i].x * scale + pts[i].y;
    return total;
}
#+end_src

A braced initializer whose last element carries a comma stays exploded, one
element per line, however short it would be -- the same "magic trailing
comma" =black= has and =clang-format= reads the same way. Remove the comma
and it collapses back onto one line:

#+begin_src cpp
int a[] = {1, 2, 3,};   // stays one per line
int b[] = {1, 2, 3};    // stays on one line
#+end_src

To keep a chained call or another expression on separate lines, end each
line you want to keep broken with a backslash. =gf= preserves the backslash
and the break, even when the whole expression would fit, and indents the
continuation lines:

#+begin_src cpp
Obj.size(2) \
    .color("green") \
    .plot(handle);
#+end_src

Keep the backslash immediately before the newline. Ordinary line breaks
within an expression can still be joined by the formatter.

It is not =clang-format=, though, and the differences are deliberate:

- *Short forms are preserved, not imposed.* =if (c) return;= and =int f() {
  return 1; }= stay on one line if that is how they were written and they
  fit. Nothing is ever *joined* onto one line that the input had apart, so
  the mixed style real C++ is written in survives instead of being flattened
  one way or the other.
- *Preprocessor directives are re-spaced but never re-wrapped.* A =#define=
  carrying a backslash continuation is emitted byte for byte, and the code
  inside a macro body is not formatted -- without expanding it there is no
  way to know whether it is a statement, an expression or a fragment of
  either. Directives go flush left, including inside a function body.
- *Greedy, not optimal, line breaking.* =clang-format= will take a worse
  break early to get a better one later; this takes the first split that
  fits. Long chained calls in particular wrap less prettily.
- *No comment reflowing.* A too-long =//= stays too long, and a block
  comment's interior is only re-indented when every line of it starts with a
  single =*=. A banner drawn with =**=, ASCII art or commented-out code is
  left byte for byte.
- *No =#include= sorting*, and nothing is ever
  inserted or rewritten that was not already there -- no braces, no =const=,
  no blank lines, and in particular no fixing up of a =\}  // namespace foo=
  comment, which =clang-format= does and which edits the code's text rather
  than its layout.
- *A macro invocation with no semicolon* (=ABSL_NAMESPACE_BEGIN=) reads as
  part of the declaration after it, because in a token stream that is
  exactly what it looks like.

** It will not rewrite code it cannot prove it preserved

A C++ formatter only ever moves whitespace, so the proof-reading is exact:
every result is re-lexed and compared against the original token for token,
spelling for spelling, with no tolerance at all except trailing whitespace
inside a comment. If that check fails -- or the file does not lex in the
first place -- =gf= reports the reason and *leaves the buffer exactly as it
was*, naming the line so the cursor can be put on it.

That check is also what licenses the guessing C++ forces on a formatter that
does not parse. Whether a =<= opens a template or compares two numbers,
whether a =*= declares a pointer or multiplies, whether a ={= opens a block
or an initializer list -- none of those can be settled without name lookup
over the whole translation unit. Guessing wrong moves a space; it cannot
move a token, and the check proves it.

There is exactly one place in C++ where the whitespace between two tokens is
*meaningful* rather than cosmetic, and the check above is blind to it because
the token streams really are identical: =#define X(a)= defines a
function-like macro and =#define X (a)= an object-like one. That single
space is carried over from the source rather than re-derived.

That is what makes the guesses C++ forces on a formatter safe. Whether a
=<= opens a template or compares two numbers, whether a =*= declares a
pointer or multiplies, whether a ={= opens a block or an initializer list --
none of those can be settled without name lookup over the whole translation
unit, so mep guesses. Guessing wrong moves a space; it cannot move a token,
and the check proves it.

#+begin_src lua
mep.format_languages.cpp.width = 120   -- default 100
#+end_src

are byte-identical to =clang-format='s with the matching style; the rest are
the deliberate differences above.

To go back to =clang-format= instead, replace the entry with an ordinary
argv one:

* The C formatter

C files are laid out exactly the way =clang-format= lays them out in its
default LLVM style, by mep itself -- no =clang-format= binary, no libclang.
It is a port of =clang-format='s own pipeline, cut down to C: the same
lexer, the same parser into lines, the same token annotation, the same
penalty-based search for where to break a long line, the same whitespace
pass. It is also what [[file:c-lsp.html][mep's C language server]] formats
with.

#+begin_src c
#include <stdio.h>
struct point{int x;int y;};
static int sum(const struct point*pts,int n,int scale){
int total=0;
for(int i=0;i<n;i++)total+=pts[i].x*scale+pts[i].y;
switch(scale){case 0:return 0;default:break;}
return total;}
#define SQUARE(x) ((x)*(x)) // squares x
#+end_src

becomes

#+begin_src c
#include <stdio.h>
struct point {
  int x;
  int y;
};
static int sum(const struct point *pts, int n, int scale) {
  int total = 0;
  for (int i = 0; i < n; i++)
    total += pts[i].x * scale + pts[i].y;
  switch (scale) {
  case 0:
    return 0;
  default:
    break;
  }
  return total;
}
#define SQUARE(x) ((x) * (x)) // squares x
#+end_src

Two-space indents, an 80-column margin, =int *p= with the star on the name,
braces on the line that opens them, =case= labels at the =switch='s own
indent, a short function kept on one line, continuation lines aligned after
the open bracket, runs of trailing comments lined up, the backslashes of a
multi-line =#define= lined up at the margin, comments that run past it
reflowed and long strings split. Every =#if= / =#else= branch is laid out,
not just the first.

On the 841 C files of mep's corpus that =clang-format= finishes (Lua,
CPython, SQLite's shell, tree-sitter), *every one* comes out byte-identical
to =clang-format --style="\{BasedOnStyle: LLVM, SortIncludes: Never\}"= --
about 700,000 lines. The one difference by design:

- *=#include= lines are never reordered.* LLVM style sorts them within each
  block; in C the order of includes can matter.

Like =clang-format=, a handful of files only settle on a second =gf= (8 of
the 841 -- the same 8 for both, with the same second result).

** It will not rewrite code it cannot prove it preserved

The result is lexed again and compared with the input token for token:
only whitespace may differ, plus what reflowing a comment or splitting a
string changes -- the words of every comment and the bytes of every string
stay the same, in order -- and no token may move into or out of a
preprocessor directive. A =#define='s name keeps its =(= attached or
detached, since that space decides whether the macro takes arguments. If
the check fails, =gf= leaves the buffer exactly as it was and names the
line.

Each combination of =#if= branches is a pass over the whole file, so a file
with very many of them costs that many passes. =clang-format= has the same
cost and no limit: on SQLite's 9 MB amalgamation (=sqlite3.c=) it runs for
minutes and takes tens of gigabytes. mep counts the combinations on the
first pass and refuses up front, with a message, when the file is too large
for them; anything up to about a megabyte with a hundred-odd combinations
(SQLite's =shell.c=) is still formatted.

** Options

#+begin_src lua
mep.format_languages.c.width = 100        -- ColumnLimit, default 80
mep.format_languages.c.indent = 4         -- IndentWidth, default 2
mep.format_languages.c.tabs = true        -- UseTab: ForIndentation; a tab is
                                          -- `indent` columns, 8 when unset
mep.format_languages.c.case_indent = true -- IndentCaseLabels
#+end_src

A project's own =.clang-format= is not read. To use =clang-format= itself
(and with it the project's =.clang-format=), replace the entry with an
ordinary argv one:

#+begin_src lua
mep.format_languages.c = {'clang-format', '--assume-filename={}'}
#+end_src

=.h= files go to the C++ formatter, which is what a header is in a C++
project; in a C project, send them here instead:

#+begin_src lua
mep.format_languages.h = mep.format_languages.c
#+end_src

The port follows =clang-format= (part of LLVM, Apache License 2.0 with LLVM
exceptions); =src/c_format_internal.h= carries the attribution.

* The Python formatter

Python is formatted by mep itself. Nothing is spawned, nothing has to be on
=PATH=, and =gf= works the same in a fresh checkout as on a fully set-up
machine.

It is shaped after =black=, because that is what a Python buffer is expected
to look like: 4-space indents, double quotes, 88-column lines, one argument
per line with a trailing comma once a call has to be exploded, two blank
lines around top-level =def= and =class=.

It is not =black=, though, and the differences are deliberate:

- *No invented parentheses.* =black= wraps a too-long =return a and b= in
  parentheses of its own so it can split it. mep's does not, so a long line
  with no bracket in it stays long rather than being restructured.
- *=match= statements are left alone.* =match= and =case= are ordinary
  identifiers until they are not, and telling the two apart needs a real
  parser.
- *Comments are normalized, not moved.* They keep the token they follow.

** Indentation alone, on every save

=gf= is the whole formatter. The much smaller half of it -- put the
indentation back on the four-space grid and change nothing else -- runs on its
own every time you save a Python buffer, which is what fixes a block pasted
from a two-space or tab-indented source. It is =:set pyindent= (on by default;
see [[file:options.html][Options]]), it shares this formatter's tokenizer and its proof-reading,
and it leaves a file it cannot read unambiguously completely alone.

** It will not rewrite code it cannot prove it preserved

Every result is proof-read before it reaches the buffer: the formatted text
is re-tokenized and compared against the original, allowing only the changes
the formatter is entitled to make (whitespace, quote style, numeric literal
case, and the trailing commas an exploded bracket gains).

If that check fails -- or the file does not parse in the first place -- =gf=
reports the reason and *leaves the buffer exactly as it was*. A syntax error
names its line, so the cursor can be put on it.

** Options

#+begin_src lua
mep.format_languages.py.width = 100   -- default 88
#+end_src

To go back to =black= instead, replace the entry with an ordinary argv one:

#+begin_src lua
mep.format_languages.py = {'black', '--quiet', '--stdin-filename={}', '-'}
#+end_src

* The Maxima formatter

Maxima has no formatter of its own to defer to -- its =grind= is a printer
for *values*, and running a file through it would lose the file's comments
and its =$= terminators. So mep's own follows the style =grind= prints in
where that style is also what real Maxima is written in, measured against
the 657 =.mac= files Maxima's distribution ships:

| Written        | Because                                          |
|----------------+--------------------------------------------------|
| =f(x)=         | a call's parenthesis is tight (113,051 files to 22,752) |
| =a+b=, =u^2=   | arithmetic is dense (18,040 to 3,378)            |
| =a > 0=, =p and q= | comparisons and logic are spaced             |
| =x : 1=, =f(u) := u^2= | assignment and definition are spaced     |
| =f(a, b)=      | a comma is followed by a space                   |

The rule behind the last two is *structure is spaced, arithmetic is
dense*, so =a : x+y= shows at a glance which part is the assignment and
which is the sum.

#+begin_src maxima
f(x,y):=block([a:1,b],a:x+y,if a>0 then b:a else b:-a,return(b))$
#+end_src

becomes

#+begin_src maxima
f(x, y) := block([a : 1, b],
  a : x+y,
  if a > 0 then b : a else b : -a,
  return(b))$
#+end_src

A =block= keeps its local list on the opening line and puts one statement
per line under it. A list packs to the margin instead, because a list is
usually data. A long conditional breaks before =then= and =else=.

Three things are never touched, because in Maxima they are meaning rather
than layout: a statement's terminator (=;= displays the result, =$= does
not), a string's escapes, and the spelling of a loop clause (=for i : 1=
and =for i from 1= are the same loop, and each is left as it was written).

* The Bash formatter

Shell scripts are laid out the way =shfmt= lays them out, by mep itself:
the same parser mep's [[file:bash-lsp.html][Bash language server]] uses
reads the script, and the tree is printed back.

#+begin_src sh
greet () {
  local name=$1
    if [ -n "$name" ]
    then
  echo "hi $name";
  fi
}
for x in a b;do greet $x;done
#+end_src

becomes

#+begin_src sh
greet() {
  local name=$1
  if [ -n "$name" ]; then
    echo "hi $name"
  fi
}
for x in a b; do greet $x; done
#+end_src

- =then= and =do= go on the line that opens the block, one statement per
  line inside it; a block written on one line with a single statement in
  each body (=[[ -f x ]] || { echo no; exit 1; }= has two, so it opens up)
  stays on one line.
- Single spaces between words and around =|=, =&&= and =;;=; =name()=;
  redirections tight to their target (=>file=, =2>&1=), and moved after the
  arguments unless written right after the command name, as =shfmt= does.
- Arithmetic re-spaced: =$((a + 1))=, =((i++))=, =for ((i = 0; i < n; i++))=.
- Backquotes become =$(...)=.
- A line broken after =&&=, =||= or =|=, or with a backslash inside a
  command, stays broken there, one level in.
- Comments stay where they are, a run of trailing comments is lined up, and
  at most one blank line is kept between statements.
- Here-document bodies are kept byte for byte (a =<<-= body, whose leading
  tabs bash strips, is re-indented when the file indents with tabs).

The indent unit is the file's own -- tabs, or the width of spaces its
blocks are indented by -- and so is whether =case= patterns sit a level
inside the =case=. A file with nothing indented yet gets tabs.

On the 3,432 scripts of mep's Bash test corpus (bash-completion, git's test
suite, bash's examples and tests, every =.sh= in nixpkgs), with tabs, 96% of
files come out byte-identical to =shfmt='s output and 99.9% of lines. The
rest are deliberate:

- *Array subscripts are left as written.* =shfmt= re-spaces =a[i+1]= as
  arithmetic, which for an associative array changes the key:
  =[x86_64-linux]= becomes =[x86_64 - linux]=. nixpkgs has update scripts
  that =shfmt= breaks that way.
- *=${x/pat}= is not rewritten* to =${x/pat/}=, and nothing inside =${...}=
  is re-spaced.
- *Here-document bodies are not formatted*, not even the =$(...)= in them.
- *Backquotes holding nested backquotes, or written right after a =$=, stay
  backquotes.*

** It will not rewrite a script it cannot prove it preserved

The result is parsed again and compared with the original, command by
command and word by word, comments and here-document bodies included; only
the layout may differ. A script that does not parse, or a layout that would
change anything else, leaves the buffer exactly as it was and says why --
with the line, for a syntax error.

** Options

#+begin_src lua
mep.format_languages.sh.indent = 2              -- two spaces, whatever the file uses ('\t' for tabs)
mep.format_languages.sh.case_indent = true      -- case patterns a level inside `case`
#+end_src

To use =shfmt= instead:

#+begin_src lua
mep.format_languages.sh = {'shfmt', '--filename', '{}'}
mep.format_languages.bash = mep.format_languages.sh
#+end_src

* The SQL formatter

SQL files are laid out by mep itself, over the same SQLite parser mep's
[[file:sql-lsp.html][SQL language server]] uses, in the common "one clause
per line" style that sqlfluff's and pgFormatter's defaults both produce:

#+begin_src sql
select o.id,c.name,sum(o.total) as spent from orders o join customers c on c.id=o.customer_id where o.status='paid' and o.created_at>date('now','-30 days') group by o.id,c.name order by spent desc limit 10;
#+end_src

becomes

#+begin_src sql
SELECT o.id, c.name, sum(o.total) AS spent
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.status = 'paid' AND o.created_at > date('now', '-30 days')
GROUP BY o.id, c.name
ORDER BY spent DESC
LIMIT 10;
#+end_src

- Keywords in upper case; names, strings and comments exactly as written
  (a type name such as =integer= is a name to SQLite, and so is a keyword
  used as one: a column called =key=, the =replace()= function).
- One clause per line: =SELECT=, =FROM=, each =JOIN= (with its =ON= or
  =USING= on the same line when it fits, else indented below), =WHERE=,
  =GROUP BY=, =HAVING=, =WINDOW=, =ORDER BY=, =LIMIT=; =INSERT INTO=,
  =VALUES=, =ON CONFLICT=, =RETURNING=; =UPDATE=, =SET=; =DELETE FROM=;
  the =UNION= between two =SELECT=s on a line of its own.
- A clause's list stays on the clause's line when it fits in the width,
  else one item per line, a level in, with trailing commas. A =WHERE= or
  =HAVING= that does not fit breaks before each top-level =AND= / =OR=.
- Subqueries and CTE bodies are indented a level inside their
  parentheses, the =)= back at the start; a call or list that does not fit
  opens up the same way, and so does a long =CASE= (one =WHEN= per line).
- =CREATE TABLE= gets one column definition or constraint per line, the
  types lined up; =CREATE TRIGGER='s body statements are formatted as
  statements between =BEGIN= and =END=; a virtual table's module
  arguments are left exactly as written (the module parses them, not
  SQLite).
- Comments stay where they were; blank lines between statements are
  kept, at most one. The =sqlite3= shell's =.commands= lines and the
  =-- database:= header pass through untouched.

** It will not rewrite a script it cannot prove it preserved

The result is tokenized again and must be the same tokens as the input,
comments included, apart from whitespace and the case of keywords, and
must parse without error. A file with a syntax error -- by SQLite's
rules, so a PostgreSQL-only statement counts -- is left exactly as it was,
with SQLite's message and the line.

On SQLite's own test suite (40,356 SQL blocks) and every =.sql= file in
nixpkgs' sources (2,884 files):

| corpus        | formatted | refused | at a syntax error SQLite reports too | not idempotent | SQLite's verdict changed | crashes |
|---------------+-----------+---------+--------------------------------------+----------------+--------------------------+---------|
| SQLite tests  |    40,085 |     271 | 242                                  |              0 |                        0 |       0 |
| nixpkgs .sql  |       577 |   2,307 | 2,286                                |              0 |                        0 |       0 |

The other refusals are errors SQLite raises while parsing that its
syntax-only check does not ("ORDER BY clause should come after UNION ALL
not before"), or syntax errors after an earlier statement where SQLite
had already stopped on a semantic error. Most of nixpkgs' =.sql= files are
PostgreSQL or MySQL. "Verdict changed" re-runs each statement of the
formatted file through SQLite and compares the result -- error or not, and
which error -- with the original's. The corpus runs clean under
AddressSanitizer and UndefinedBehaviorSanitizer.

Compared with sqlfluff (=--dialect sqlite=) and pgFormatter on mep's
example files, the layout of clauses, subqueries and CTEs is the same; the
differences are deliberate: a short select list stays on the =SELECT= line
(sqlfluff always puts several targets on lines of their own), =CREATE
TABLE= column types are aligned, a =VALUES= list that does not fit gets
one row per line, and no rewriting beyond layout and keyword case
(sqlfluff's =fix= also turns =JOIN= into =INNER JOIN= and reorders =ON=
comparisons).

and =.asd= files, the Enter key's auto-indent in those buffers uses the same
rules, and it is what
[[file:lisp-lsp.html][mep's Common Lisp language server]] formats with.

- Indentation as =common-lisp-indent-function= computes it: the specs of

  under its first, a keyword under the keyword above it.
- No space just inside parens -- =( foo )= is =(foo)= -- and a close paren

  comment or the paren carries a comment of its own.
- No trailing whitespace, at most two blank lines in a row, a final newline

The result is read again and its tokens compared with the input's; only
whitespace may differ. A file that does not read -- an unclosed paren or
string -- leaves the buffer exactly as it was, and =gf= says why, with the

becomes

What it does:

- Indentation as =scheme-indent-function= computes it:
  - all 84 of scheme.el's specs: =lambda=, =let=, =when=, =do=,
    =syntax-rules=, =dynamic-wind=, =parameterize=, =match=...;
  - a named =let= has one more distinguished form;
  - any =def...= head, in any case, is indented as a definition;
  - a call's arguments line up under the first one;
  - a list whose car is not a symbol lines up under its first element.
- Square brackets are parens.
- The same whitespace rules as the Common Lisp formatter:
  - no space just inside parens;
  - a lone close paren joins the line before it;
  - no trailing whitespace;
  - at most two blank lines in a row;

- the text of strings and =|...|= symbols;
- =;= comments, =#|...|#= comments and =#;DATUM= comments;
- character literals such as =#\(=.

It does not wrap, so it has no =width=.

It is checked against Emacs 30's own =indent-region= on 3,557 files: Guile,
Guix, haunt, guile-lib, chibi, Chez and Gauche
(=tools/scheme_indent_oracle.el=, =just format-compare scheme=). Of the
3,549 files mep formats, 3,532 come out byte-identical, and each is a

reads as code text that is not code, and sometimes changes the program:

- Guile's =#!...!#= block comments;
- the text after a top-level =#!eof=;
- a multi-line =#{...}#= symbol;
- Gauche's =#[ ]= character sets.

Also on purpose, as in the Common Lisp formatter, these lines keep their
indentation:

- a line inside a =#|= or =#;= comment;
- a line holding only a single-=;= comment.

The 8 files it leaves alone use Chez or Gauche reader syntax that mep does
not read.

As with Common Lisp, the result is read again and compared token by token
with the input. A file that does not read is left exactly as it was, with
the reason and the line.

the places where it would change what the script does: an empty array
index (=$a()=) keeps its parentheses, a comment that a trailing =\=
continues onto a blank line keeps that blank line (otherwise the next
command would become part of the comment), and =expr {$}= is left alone
rather than emptied. A file that does not parse, or is not UTF-8, leaves
the buffer as it was and =gf= says on which line it stopped; so does
nesting more than 200 scripts deep.

** Options

#+begin_src lua

#+end_src

Reproduce the numbers with =just format-compare tcl= (needs
=just grammar-corpus tcl= first).

* The Octave formatter

Octave and MATLAB files get the layout of MISS_HIT's =mh_style --fix= --
the style checker of the MISS_HIT tools -- produced by mep itself, with no
Python and no MISS_HIT installed. It is not a pretty-printer: every line
keeps its tokens and the spaces between them except where a rule says
otherwise.

#+begin_src octave
function r=sign2(x)
%returns the sign
if (x>0), r=1;
elseif x<0
	r = -1 ;
else r=0; end
v = [1, 2,];
w = f((a+b), c) .^ 2;
#+end_src

becomes

#+begin_src octave
function r = sign2(x)
    % returns the sign
    if x > 0
        r = 1;
    elseif x < 0
        r = -1;
    else
        r = 0;
    end
    v = [1, 2];
    w = f(a + b, c).^2;
#+end_src

What it does:

- *Indentation*: four columns per level -- a function's body, each branch
  of =if=, loops, =try=/=catch=, =switch= and once more for each =case=,
  classdef sections -- with comments following the code around them.
  Continuation lines (after =...=, or inside brackets) line up one column
  inside the bracket they are in, or keep their offset from the
  statement's first token.
- *Spaces*: one around binary operators and ~=~, after =,= and =;= and
  after keywords; none inside brackets, around =:= and =^= =.^=, or after a
  unary operator; =%comment= becomes =% comment=.
- *Statements*: one per line (=if x, y = 1; end= is split), extra =;= and
  =,= removed, a comma or semicolon a matrix row does not need removed
  (=[1, 2,]=), brackets around a whole condition, range or argument removed
  (=if (x)=, =f((a))=).
- *Blank lines*: at most one in a row, one around each function, none at
  the start; trailing whitespace and tabs gone; one final newline.

Octave's own syntax -- =endif= and the other =end= keywords, =do= ...
=until=, =unwind_protect=, =#= comments, =!= and ~!=~, =++= -- is laid out
like its MATLAB counterpart. Block comments (=%{= ... =%}=) and command
syntax (=hold on=) are left as they are.

Of the 6,676 files of Octave's own scripts and tests and of 30 Octave Forge
packages, =mh_style= fixes only 3,020: it rejects =endif= and most other
Octave syntax. On those, run as one =mh_style --fix= run exactly
(=mep-octave-format-test --mh-style=), mep is byte-identical on 2,976 of
the 3,018 it accepts (98.6%; 99.95% of lines). The 42 that differ are the
ones listed below, plus =do= ... =until=, which =mh_style= reads as a
statement named =do=, and comments with non-ASCII bytes, which =mh_style=
reads as Windows-1252 and writes back as =�=; mep keeps the bytes.

** Where it differs from =mh_style=, and why

- =mh_style= ends every statement with =;=, which changes what Octave
  prints -- =x = 1= shows =x=, =x = 1;= does not. mep leaves that out by
  default, and a =,= that ends a statement is removed rather than turned
  into =;=. =semicolons = true= puts the rule back.
- =mh_style= is not idempotent: it lines continuation lines up with the
  columns their first line had /before/ its own spacing was fixed, so a
  second run can move them again. mep runs to a fixed point, so formatting
  twice changes nothing.
- =if (x), y = 1; end= -- =mh_style= removes the brackets and with the
  closing one loses the line break it wanted there, writing =if x y = 1;=,
  which no longer parses. mep breaks the line.
- Octave syntax MATLAB lacks gets Octave's reading: a condition in brackets
  that runs over lines without =...= keeps its brackets (without them the
  line break would end the statement), a comment line inside a =...=
  statement keeps the =...= before it, and a postfix =++= sits against its
  operand like a transpose.
- =[min(p) max(p)]([1 3 2 4])= -- =mh_style= drops the second pair of
  brackets as redundant, which changes the meaning. mep only removes
  brackets when the tree is the same without them.

** It will not rewrite a file it cannot prove it preserved

The result is parsed again by mep's Octave reader -- the same one whose
errors match Octave's (see [[file:octave-lsp.html][The Octave language server]])
-- and must give the same tree as the input, brackets aside. A file Octave
would reject leaves the buffer as it was and =gf= says on which line it
stopped. Over the whole corpus, in the default mode, every one of the 6,654
files Octave accepts is formatted and passes this check, and formatting the
result again changes nothing; the 22 it leaves alone are the 22 Octave
rejects.

** Options

#+begin_src lua
mep.format_languages.m.indent = 2         -- mh_style's tab_width
mep.format_languages.m.semicolons = true  -- end every statement with ;
#+end_src

Reproduce the numbers with =just format-compare octave= (needs
=just grammar-corpus matlab= first; it fetches MISS_HIT from nixpkgs).

* The Julia formatter

Julia files get Runic's style -- the "no options" formatter, Julia's
answer to gofmt -- and mep produces it itself, with no Julia installed: the
formatter is a port of Runic.jl 1.5.0, pass for pass, walking the trees of
mep's port of JuliaSyntax 0.4.10, the parser Runic is built on.

#+begin_src julia
function f(x,y)
  z=x+y
  for i=1:10 println(i) end
  if z>1 return z end
  z
end
#+end_src

becomes

#+begin_src julia
function f(x, y)
    z = x + y
    for i in 1:10
        println(i)
    end
    if z > 1
        return z
    end
    return z
end
#+end_src

Like Runic it indents with four spaces, puts single spaces around
operators, assignments and keywords (but none around =:=, =^= and =::=),
spaces lists after their commas, writes =in= in loops, adds an explicit
=return= to functions (not after =throw= or =error=), puts braces around a
=where= clause and parentheses around operator calls in ranges
(=a:(b + 1)=), spells numbers =0x01= and =1.0=, drops trailing semicolons
and blank lines beyond two, and leaves alone what lies between
=#! format: off= and =#! format: on=. It does not wrap long lines: Runic
never moves code between lines except to open a one-line block.

Over 8,216 files -- Julia's own base and standard library plus eleven
packages -- every file Runic formats (8,210; it refuses 6) comes out
byte-identical to Runic's output. Runic is not quite idempotent (8 of those
files change again when formatted twice, a trailing comma or a space after
=end=); mep follows it there too.

** It will not rewrite a file it cannot prove it preserved

A file that does not parse leaves the buffer as it was, and =gf= gives the
parser's message and line. Where Runic would stop with an internal
assertion, mep stops too. The result is parsed again, and its tokens --
everything but whitespace -- compared with the input's, allowing only the
token changes Runic makes on purpose (commas, semicolons, the parentheses
and braces above, =return=, =in=, number spellings); anything else leaves
the buffer alone.

* The C# formatter

mep lays C# out the way =dotnet format whitespace= does with no
=.editorconfig= -- four-space indentation, braces on their own lines, its
spacing rules -- and it does so itself, with no .NET: the formatter is a
port of Roslyn's own formatting engine (the C# formatting rules and the
engine that applies them, at the commit the .NET 10 SDK's =dotnet format=
was built from), running on mep's port of Roslyn's parser, whose trees are
Roslyn's own. It is also what
[[file:csharp-lsp.html][mep's C# language server]] formats with.

#+begin_src csharp
namespace Shapes{
public class Polygon {
  int sides=3;
public  int Sides{get{return sides;}set{sides=value;}}
public double Angle( ){
if(sides<3){throw new System.ArgumentException("too few sides");}

#+end_src

becomes

#+begin_src csharp
namespace Shapes
{
    public class Polygon
    {
        int sides = 3;
        public int Sides { get { return sides; } set { sides = value; } }
        public double Angle()
        {
            if (sides < 3) { throw new System.ArgumentException("too few sides"); }
            return 180.0 * (sides - 2) / sides;
        }

#+end_src

Like Roslyn's, it fixes whitespace and indentation and nothing else: it
moves braces of types, members and blocks onto their own lines, but keeps a
block, property or statement the author wrote on one line on one line; it
spaces operators, commas, casts and keywords, indents blocks, switch
sections, embedded statements, lambdas, initializers, collection
expressions, patterns and query clauses, re-indents comments, doc comments
and =#region= lines with the code, puts other directives at column 0, and
leaves =#pragma warning disable format= regions alone. It never joins or
breaks lines to fit a width, and it keeps the user's own indentation of a
continued argument or expression.

All 324 of Roslyn's own formatting tests that are a plain input and
expected text (=AssertFormatAsync=, default options) give Roslyn's answer.
On mep's C# corpus (17,828 files: Roslyn's compilers, analyzers and tests,
jellyfin, osu!, OpenRA, Pinta, ILSpy, ArchiSteamFarm, OmniSharp and more),
every file comes out byte-identical to =dotnet format whitespace= but one,
and so do all 17,828 copies with their indentation and spacing scrambled.
Formatting twice changes nothing on every file of the corpus; on 613 of the
scrambled copies a second pass moves a continued argument's contents again
-- exactly as Roslyn's own second pass does.

Like =dotnet format=, a file with syntax errors is still formatted (the
space next to a missing token is left as it is), and a byte-order mark is
kept. The one difference is deliberate: a file that is not valid UTF-8 is
refused -- =dotnet format= reads it with replacement characters and writes
them back, losing the original bytes (the one corpus file is Shift-JIS).

** It will not rewrite a file it cannot prove it preserved

The result is parsed again and compared with the input's tree: every node
and token, the same syntax errors, the same comments and directives up to
whitespace. If anything else differs, the buffer is left as it was and =gf=
says where.

* The R formatter

mep's R formatter follows the tidyverse style: two-space indent, spaces
around binary operators (but not around =^=, =:=, =::=, =$= or =@=), =<-=
for assignment, double-quoted strings, and an 80-column margin that calls,
argument lists and pipelines are broken across to respect.

#+begin_src r
result=some_function(argument_one=1,argument_two=2,argument_three='three')
#+end_src

becomes

#+begin_src r
result <- some_function(
  argument_one = 1,
  argument_two = 2,
  argument_three = "three"
)
#+end_src

A trailing block "hugs" the call it belongs to rather than exploding the
argument list, which is the shape R is actually written in:

#+begin_src r
test_that("it works", {
  expect_equal(1, 1)
})
#+end_src

Two things it deliberately does *not* do: it never adds braces to an
=if=/=for= body that has none, and it never rewrites a =%>%= into a =|>=.
Both change the code rather than its layout, which is not what =gf= is
for.

Comments are kept where they were written -- above a statement, after it,
or after the operator they follow -- and one blank line between statements
survives (several collapse to one).

A file it cannot parse is left *completely alone*: =gf= reports the line
the parse failed on and the buffer is untouched. So is a file where the
formatter's own check -- it re-reads its output and compares it, token for
token, against the input -- finds a difference it did not intend.

* Line width

The built-in formatters wrap at *100 columns* for C++ and Nix, *88* for Python
and *80* for C, R and SQL -- =width= in each one's table entry, and the subsections
above change it. The Bash one does not wrap: like =shfmt=, it keeps a
script's own line breaks, and so do the Clojure, Common Lisp, Crystal,
C# and Tcl ones.
=clang-format=, if you put it back for C or C++, takes its margin from the
project's own =.clang-format= instead.

* Adding one

#+begin_src lua
mep.format_languages.js = {'prettier', '--stdin-filepath', '{}'}
mep.format_languages.ts = mep.format_languages.js
#+end_src

The entry is an argv array. =\{\}= anywhere in it is replaced by a path.

Three modes:

- *filter* (the default): the buffer is written to the formatter's stdin and
  its stdout replaces the buffer. =\{\}= is the buffer's real absolute
  filename.
- *file*: add =mode = 'file'=, and =\{\}= is a temporary file the formatter
  edits in place.
- *builtin*: no program at all -- =\{builtin = 'format_python', name = '...',
  width = 88\}= names a =mep.*= function taking the text and a width and
  returning the formatted text, which runs in-process. This is how every
  built-in entry above is wired.

Entries are looked up by *bare extension*, so every extension of a language
needs its own key -- which is why the built-in table aliases =.h=, =.cc=,
=.hpp= and the rest onto the C++ entry.

* Why the placeholder matters

A formatter reading stdin has no idea what file it is looking at.
=clang-format= and =air= have to be told -- =--assume-filename= and
=--stdin-file-path= -- or they cannot find the =.clang-format= or =air.toml=
the project configures them with, and they silently format to their own
defaults instead. (A =builtin= entry has no such problem: it is handed the
text directly and takes its options from its own table entry.)

So a filter-mode entry should almost always pass =\{\}= somewhere.
