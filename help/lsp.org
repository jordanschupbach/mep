* Attaching

Open a file mep has a server for, and if that server is on =$PATH= it
starts automatically. Nothing to configure.

A client runs *per language per workspace root*, so two workspaces on two
branches each get their own -- which is what makes branch-per-workspace
work without servers fighting over one project.

=:MepLspAttach= attaches by hand; =:MepLspStop= stops a client.

* The keys

| Key            | Does                          |
|----------------+-------------------------------|
| =K=            | hover documentation           |
| =gd=           | go to definition              |
| =Q=            | this line's diagnostics, in a popup |
| =]e= / =[e=    | next / previous error, then its popup |
| =<leader>li=   | go to implementation          |
| =<leader>lt=   | go to type definition         |
| =<leader>lk=   | signature help                |
| =<leader>rn=   | rename the symbol             |
| =<leader>ca=   | code action                   |

Note =gd= and not =gr=: =gr= is bound to *run* in mep, not references. For
references use =:MepLspReferences=.

Every action also has a command: =:MepLspHover=, =:MepLspDefinition=,
=:MepLspReferences=, =:MepLspImplementation=, =:MepLspTypeDefinition=,
=:MepLspSignatureHelp=, =:MepLspRename=, =:MepLspCodeAction=,
=:MepLspFormat=.

* Parameter hints

Type an opening =(= and the signature of what you are calling appears in a
popup by the cursor -- every parameter, its type annotation where the
definition has one, its default where it has one -- plus which argument you
are on right now and the callee's docstring:

#+BEGIN_EXAMPLE
connect(host: str, port: int=8080, *, timeout: float | None=None) -> bool
argument 2: port: int=8080
Open a connection to a host.
#+END_EXAMPLE

It follows you across the commas, updates as you type, and closes itself
when the cursor leaves the argument list (=Esc= dismisses it early). When the
completion list is open it moves above the line rather than covering it, so
you can read both at once.

On by default; =mep.lsp_signature_help_auto = false= in =init.lua= turns it
off, leaving it available on demand on =<leader>lk= and
=:MepLspSignatureHelp=.

How much you get depends on the server. mep's own Python and C++ servers
read the definition out of the file you are editing, so a local =def= gives
you its real annotations and defaults; for an imported name they answer from
their built-in standard-library tables, which is a signature but not a
docstring for everything.

* Diagnostics

Errors, warnings and hints are underlined in the buffer and marked in the
sign column. =Q= shows the current line's diagnostics in a popup, and
=:MepDiagShow= lists them.

=]e= and =[e= jump to the next and previous *error* in the file (wrapping
at either end), then pop up that line's errors. For diagnostics of any
severity there are =mep.lsp_next_diagnostic= and =mep.lsp_prev_diagnostic=,
unbound by default -- =mep.map_bracket_next('d', mep.lsp_next_diagnostic)=
puts them on =]d=/=[d=.

The popup is a list, one entry per diagnostic -- long messages are wrapped
but stay a single entry:

| Key                | Does                                       |
|--------------------+--------------------------------------------|
| =C-n= / =C-p=      | next / previous entry (=j= / =k= too)      |
| =y=                | copy that message to the system clipboard  |
| =Y=                | copy every message in the popup            |
| =Enter=            | jump to that diagnostic's own line:column  |
| =Esc=              | dismiss                                    |

The gutter mark says which kind, by shape as well as by colour:

| Mark                          | Severity    |
|-------------------------------+-------------|
| a disc with an =x=            | error       |
| a hazard triangle with a =!=  | warning     |
| a disc with an =i=            | information |
| a disc with a =?=             | hint        |

So a glance tells you an error from a warning without having to know the
theme's red from its yellow -- and so does a reader who cannot tell them
apart at all.

The worst severity on a line is the one its mark shows. When a line has
more than one, the message beside it is prefixed with the count -- =(3)
...= -- so nothing is lost by the mark naming a kind rather than a number.

Severity maps to the =Error=, =Warn=, =Info= and =Hint= [[file:highlight-groups.html][highlight groups]], so
the colours follow your theme.

* Semantic highlighting

Colour by what a name *is*, not by where it sits. A grammar can see that a
name is written inside a parameter list; only a server knows that the bare
=factor= three lines further down is that same parameter. A server that
answers =textDocument/semanticTokens= gets those answers drawn over the
Treesitter colours, which stay underneath for everything the server does
not claim.

Out of the box:

| Token type           | Colour   | What it fixes                           |
|----------------------+----------+-----------------------------------------|
| =parameter=          | =Red=    | a parameter, everywhere in its body     |
| =parameter.implicit= | =Cyan=   | Python's =self= / =cls=, kept as builtins |
| =namespace=          | =Orange= | an imported module, wherever it is used |
| =function=, =method= | =Blue=   | a function named rather than called     |

The table is =mep.lsp_semantic_hl=, keyed by the LSP token-type name and
optionally by =type.modifier=, which is checked first:

#+begin_src lua
mep.lsp_semantic_hl['variable.readonly'] = 'Cyan'  -- constants
mep.lsp_semantic_hl.class = 'Orange'               -- every server's classes
mep.lsp_semantic_hl.parameter = nil                -- back to the grammar's colour
#+end_src

It is short on purpose: a token type mapped here overrides the grammar in
*every* language at once. What is left out -- =variable=, =property=,
=class=, =type= -- is left out because [[file:syntax.html][Treesitter]] already colours those from
the syntax, and a second opinion would only mean a name whose colour
depends on which pass ran last.

Tokens refresh whenever the server is told about an edit -- when you stop
typing, on opening a file and on switching back to one -- and on
=:MepLspSemanticTokens=. =mep.lsp_semantic_auto = false= stops the
automatic refresh, leaving the command.

* The seven mep brings itself

=mep-org-lsp=, =mep-r-lsp=, =mep-python-lsp=, =mep-cpp-lsp=, =mep-c-lsp=,
=mep-maxima-lsp= and =mep-mepml-lsp= are mep's own servers, built and
installed alongside =mep=, so org, R, Python, C++, C, Maxima and mepml
files get diagnostics and completion with nothing to install. See
[[file:org-lsp.html][The org language server]], [[file:r-lsp.html][The R language server]],
[[file:python-lsp.html][The Python language server]], [[file:cpp-lsp.html][The C++ language server]],
[[file:c-lsp.html][The C language server]], [[file:maxima-lsp.html][The Maxima language server]] and
[[file:mepml-lsp.html][The mepml language server]].

Python, C++ and C are the three languages where mep's own server is
preferred over an external one out of the box: =pyright= and =clangd=
stay registered but claim no filetype of their own, and one line in
=init.lua= swaps either back. =.h= goes to the C++ server, which reads C
as well; a project whose headers are all C can hand it over with
=mep.lsp_servers.c_ls.filetypes = {'c', 'h'}=.

The R one never starts R: it parses the language itself, so a =.R= file
gets diagnostics, completion, hover and signature help on a machine with
no R installed at all. The Maxima one is the same -- and it is the only
Maxima language server there is, so nothing competes with it for =.mac=.

R's own =languageserver= package is still registered, under
=r_languageserver=, with no file types claimed. It knows what an installed
package exports, which mep's own server cannot. To prefer it:

#+begin_src lua
mep.lsp_servers.r_languageserver.filetypes = {'R', 'r'}
mep.lsp_servers.r_ls.filetypes = {}
#+end_src

* Inside org code blocks

Code blocks in an Org file get language-server support too, through a shadow
buffer per block. See [[file:org-polyglot.html][Language servers in code blocks]] for what that covers
and what it does not.

In an org file both run at once -- the org server on the markup, a real
language server on each block's contents -- and their diagnostics are merged
rather than replacing one another.
