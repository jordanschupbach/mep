* A notebook is a text buffer

Open a =.ipynb= and you get the notebook in the "percent" cell format that
Jupytext, VS Code and Spyder use: every cell starts with a =# %%= marker
(=# %% [markdown]= for markdown cells).

That means all the usual motions, edits, undo and search apply to cell
source. It is a text buffer, not a web view.

What the text cannot carry -- outputs, execution counts, ids, metadata --
is kept alongside and written back as real nbformat JSON on =:w=, with
Jupyter's own indentation so diffs stay clean.

* What you see

Each cell is drawn as a rounded card, markdown cards tinted apart from code,
and the cell under the cursor accented. A code cell shows =In [n]:= and a
clickable =Run= chip, with its outputs underneath: stdout and stderr, the
last expression's value, tracebacks, and inline =matplotlib= figures.

A toolbar across the top has =+ Code=, =+ Markdown=, =Run All=, =Interrupt=,
=Restart= and =Clear=.

* Running cells

No =jupyter_client= is required.

| Key              | Does                                 |
|------------------+--------------------------------------|
| =Enter=          | run the cell under the cursor        |
| =Ctrl+Enter=     | the same                             |
| =Ctrl-C Ctrl-C=  | the same, and works in Insert mode   |
| =Shift+Enter=    | run it and move to the next cell     |
| =mod1+Enter=     | run it and insert a new cell below   |
| =]j= =[j=        | next / previous cell                 |

* The =<leader>j= group

| Key          | Does                        |
|--------------+-----------------------------|
| =<leader>jr= | run this cell               |
| =<leader>jA= | run all cells               |
| =<leader>jo= | run this cell, insert below |
| =<leader>ja= | insert a cell above         |
| =<leader>jb= | insert a cell below         |
| =<leader>jd= | delete this cell            |
| =<leader>jy= | make this cell code         |
| =<leader>jk= | move this cell up           |
| =<leader>jC= | clear all outputs           |
| =<leader>ji= | interrupt the kernel        |
| =<leader>j0= | restart the kernels         |
| =<leader>jK= | set this cell's kernel      |

=:NotebookNew [path]= creates one, and the other actions have =:Notebook*=
commands too.

* Per-cell kernels

Each code cell picks its own kernel, from the dropdown at its top right (or
=<leader>jK=). Out of the box the list offers Python 3 plus whichever of R,
JavaScript (Node), Ruby and Bash are on =$PATH=.

Python 3 and R are each one *persistent* process, so state and inline
figures carry across cells: R sends back every page a cell draws (base
graphics or an auto-printed =ggplot=) as an inline PNG. R needs the =jsonlite=
package, which anything that can knit an =.Rmd= already has. The others are
stateless "script" kernels: each run is a fresh
process fed the cell's code on stdin.

A cell with no explicit choice follows the notebook default, and a new cell
inherits the previous cell's kernel -- so a block of cells keeps running on
whatever the one above it used. Each choice is written to that cell's
=metadata.kernel= on =:w=.

=In [n]:= counts up as one shared sequence across every kernel, and runs
execute one at a time in order, so a mixed "run all" still goes top to
bottom.

#+begin_src lua
mep.opt.notebook_kernels = {
  {name='python3', display_name='Python 3', language='py', mode='python'},
  {name='ir', display_name='R', language='r', mode='r', command={'Rscript'}},
  {name='deno', display_name='Deno', language='js', mode='script',
   command={'deno', 'run', '-'}},
}
#+end_src

=mode= is one of:

| Mode       | Means                                              |
|------------+----------------------------------------------------|
| =python=   | the built-in persistent Python kernel; no =command= |
| =r=        | the built-in persistent R kernel; =command= is the =Rscript= to use |
| =protocol= | your own long-lived process speaking mep's JSON-line kernel protocol |
| =script=   | a fresh process per run, code on stdin             |

=language= is the Treesitter filetype the cell body is highlighted with.

The old stateless R runner is still in the list as /R (fresh process per
cell)/ (=ir-script=), for code that must not see an earlier cell's state.

=examples/notebook_example.ipynb= is a ready-made notebook to try.

* R Markdown (=.Rmd=)

An =.Rmd= opens as a notebook too, but it stays exactly the file it is: the
buffer is the document's own text, and =:w= writes it back as-is. Its cells
are its knitr chunks -- =```{r}= ... =```= -- and everything between them is
prose. A plain =```r= fence is code being /shown/, not a chunk, and never runs
(knitr would not run it either).

Each chunk is drawn as a card with =In [n]:=, its engine and a =Run= chip on
the header line, which stays editable text. What a chunk prints, and any
plots it draws, appear under its closing fence. Every R chunk runs in one
persistent R session (the kernel above), so a chunk sees what the chunks
before it defined. A =```{python}= chunk runs on the Python kernel, in its
own session.

| Key             | Does                                               |
|-----------------+----------------------------------------------------|
| =Shift+Enter=   | inside a chunk: run it (Normal or Insert mode)     |
| =Ctrl-C Ctrl-C= | inside a chunk: run it                             |
| =]j= =[j=       | next / previous chunk                              |
| =<leader>jA=    | run every chunk, top to bottom                     |
| =<leader>jb=    | insert a new chunk below                           |

Outside a chunk those keys do what they do in any text file, and plain
=Enter= never runs anything. A chunk with =eval=FALSE= is skipped, as knitr
skips it. The engine in the header picks the kernel, so the kernel dropdown
only reports it.

Outputs never go into the document -- knitr decides what a rendered report
shows. They are kept in a cache in mep's data directory instead
(=notebook-cache/=), so reopening the file brings them back. A chunk edited
while the file was closed comes back without its now-stale output.

The Run button (top right) still knits the whole document with
=rmarkdown::render= and shows the result. The R language server works inside
R chunks (hover, completion, diagnostics, go to definition), across all the
chunks of the document at once, and markdown highlighting, headings and
spell checking apply to the prose (never to the code).
