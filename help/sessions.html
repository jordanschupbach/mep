Sessions

Your layout comes back

Close mep and reopen the project, and you get what you left: the same workspaces, the same tabs, the same split arrangement at the same sizes, the same files open at the same cursor positions, your file tree, your terminals -- and the window itself back at the size and zoom you had it.

Nothing has to be enabled, and layouts are not named or managed. This is why there is no "save layout" command worth having -- see Layouts, zoom and zen.

The standard default layout -- a file tree, your readme, a terminal -- is what you get when there is nothing to restore: a project opened for the first time, a workspace created since the last save, or a saved layout that could not be rebuilt. It is a fallback, never something applied on top of a layout that did come back.

What is saved

  • the window's size, whether it was maximized, and the interface zoom (see below);
  • every workspace, and which one was active;
  • every tab, its split tree, and which pane was focused in each;
  • how each split was sized, when you have resized it;
  • each pane's file and its other buffer tabs, recorded *relative to the workspace root*;
  • each pane's cursor position and scroll position;
  • which panes were terminals, and which was the file tree.

Paths are stored relative to the workspace root, so a project that moves -- or a worktree created at a different path on another machine -- still restores.

What does not come back exactly

Three things are approximations rather than losses, and knowing which saves you looking for a bug:

  • A terminal comes back as a fresh shell, at the workspace root. Its scrollback and whatever it was running are not saved, because they cannot be -- the pane is restored, the process is not.
  • A pane's extra buffer tabs come back in saved order, with the one you were looking at last, rather than each in the exact slot it held.
  • Unsaved, unnamed buffers have no path to reopen by, so their panes come back empty. Save the buffer if you want it back.

Opening a file on the command line (mep --project <dir> <file>) is deliberately not a restore: the file you asked for is what you get. The saved layout stays on disk, ready for the next plain launch, unless you go on to rearrange panes in that session -- at which point the autosave records what you built, as it does in any other.

When it is saved

Half a second after any structural change, and again on quit. The debounce means a burst of splitting and closing costs one write, not twenty.

Closing a project saves its state on the way out, so a project you close and reopen within one session behaves the same as one you quit and relaunch.

The window itself

The window's size comes back too, along with whether it was maximized and the interface zoom (Ctrl+Shift+= / Ctrl+Shift+-). These are application-wide rather than per project -- there is only one window, and mep has to settle all three before it knows which project it will show -- so they live in their own file:

$XDG_DATA_HOME/mep/window.json

The size recorded is the one the window has when it is not maximized. A maximized window's size is the screen's, so saving that as a size would mean reopening a plain window the size of the display, and un-maximizing would have nowhere to go back to. Maximized is saved as the state it is, and the size alongside it is what the window returns to when you un-maximize -- what a window manager calls the restore geometry.

The first time you run mep there is nothing saved, and it opens maximized at the default zoom, as it always has. A file written by an older mep that saved no zoom still has its window size honoured; the zoom just falls back to the default.

Window position is deliberately not saved. Window managers place windows by their own rules, and a saved position is the kind of thing that ends up slowly walking a window off the corner of the screen across launches.

Where it is saved

$XDG_DATA_HOME/mep/workspaces/<project>-<hash>.json

<project> is a filesystem-safe lowercase form of the project directory's name, and <hash> is a short stable hash of its full path. The hash is what keeps two different checkouts that happen to share a basename -- two clones both called mep -- from overwriting each other's state.

When something has changed underneath

Restoring is forgiving by design, because the world moves between sessions:

  • a file that no longer exists is skipped -- its pane comes back empty, and you get one message saying how many were skipped;
  • a worktree that has vanished is pruned;
  • a saved layout that does not make sense -- a file hand-edited into an impossible shape, or written by a newer mep -- is declined whole, and that workspace opens with the standard default layout instead. A layout is checked before any of it is rebuilt, so you never land in half of one;
  • a corrupt or unreadable state file is ignored, and you get a fresh start rather than an error.

None of these stop the rest of the session restoring: workspaces are restored independently, so one that has to fall back to the default layout does not cost you the others.

Turning it off, or doing it by hand

HowEffect
mep --no-sessionneither restore nor save -- window size and zoom included -- this run
mep.opt.restore_workspaces = falsethe same, permanently
:wssavesave now
:wsrestorerebuild this project's saved layout now

:wsrestore rebuilds the panes of the current project from the file on disk, so the arrangement you are looking at is replaced. Buffers are not: anything you have open stays open and stays in :ls, including unsaved work, even when no pane is left showing it. Terminals whose panes go away are closed, since nothing could show them again.

--no-session is the one to reach for when you want to open a project without disturbing its saved state -- a quick look at someone else's checkout, or a scripted run.

Because init.lua runs before any restore, setting mep.opt.restore_workspaces there takes effect in time.
