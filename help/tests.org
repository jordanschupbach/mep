* Run this file's tests

=gt= (=:MepLangTest=) works out how to test the file you are looking at and
runs it in this tab's terminal.

It saves the buffer first when it is modified -- a test run against a stale
copy on disk is worse than useless -- and reports the command it chose on
the status line (and in the Notifications history), which is the only
feedback when the terminal is off screen.

| Filetype        | Runs                             |
|-----------------+----------------------------------|
| =.go=           | Go's test runner                 |
| =.py=           | the configured Python test runner |
| =.r=, =.R=      | R's test tooling                 |
| =.c=, =.cpp=, headers | the project's build-directory test target |
| =.rs=           | Cargo's test runner              |

#+begin_src lua
mep.opt.lang_test_python = {'pytest', '-q'}
mep.opt.lang_test_build_dirs = {'build', 'build/native'}
#+end_src

If mep cannot work out a runner for the filetype, it says so in one line
rather than guessing.

* The Tests panel

=<leader>tT= (=:MepActivityTestPanel=) opens the test sidebar. It looks
through the project for every test suite it knows how to run and lists
each one as its own group, so a repository with a CMake build, a Python
package and two npm packages shows all four:

| Suite       | Found when a directory has                                    | One row per         | Grouped by                 |
|-------------+---------------------------------------------------------------+---------------------+----------------------------|
| ctest       | a configured build directory (see below)                      | ctest test          | label                      |
| pytest      | a Python project marker and tests, with pytest importable     | test (node id)      | file, then class           |
| unittest    | the same, without pytest                                       | test method         | module, then class         |
| testthat    | =tests/testthat=                                               | =test_that()= block | file, then =describe()=    |
| jest        | a =package.json= naming jest                                   | test file           | directory                  |
| vitest      | a =package.json= naming vitest                                 | test file           | directory                  |
| node:test   | a =package.json= whose test script runs =node --test=          | test file           | directory                  |

A Python project marker is =pyproject.toml=, =setup.py=, =setup.cfg=,
=pytest.ini=, =tox.ini= or =conftest.py=, alongside a =tests/= or =test/=
directory or =test_*.py= files. The search goes four directories deep
(=mep.opt.activity_test_scan_depth=) and skips hidden directories, =build*=,
=node_modules= and virtualenvs. A suite found in a directory hides any more
of the same kind beneath it, because pytest or jest at the top already runs
those. The exception is a =package.json= with =workspaces=: its packages
are listed as suites of their own.

Each row has a mark for where it stands:

| Mark | Means                                       |
|------+---------------------------------------------|
| ○    | not run yet                                 |
| …    | queued in the current run                   |
| ●    | running now                                 |
| ✓    | passed (with how long it took)              |
| ✗    | failed, timed out, or its build failed      |
| -    | skipped                                     |

Within a suite, tests sit in groups, nested the way the runner nests them
(see the table above). Each group's row counts what is under it -- =✗2 ✓5
○1= -- leaving out what is zero.

Press Enter on a test to run just that test, on a group to run everything
in it, or on a suite's heading to run that suite. Enter on the =all= row at
the top runs every suite, one after another. The marks update live as each
runner reports.

| Key   | Does                                                       |
|-------+------------------------------------------------------------|
| Enter | run the test, group, suite or (top row) everything under the cursor |
| =a=   | run every suite                                            |
| =f=   | re-run only the tests that failed, in every suite          |
| =o=   | show the output of the test, group or suite under the cursor |
| =c=   | fold or unfold the group (or suite) under the cursor       |
| =x=   | stop the run                                               |
| =R=   | look for suites again and re-list their tests              |

=o= on a failed test shows its traceback, testthat's failure summary, or
Jest/Vitest/Node's message for that file. For a ctest test whose build
failed, it shows the build log, compiler error included. On a suite's
heading it shows that suite's last run; on a group, the output of every test
in it that failed; on the top row, every suite's. The
popout (=mod1+m=) shows the same output beside the list as you move
through it.

** What runs each suite

| Suite     | Runs                                                              |
|-----------+-------------------------------------------------------------------|
| ctest     | =cmake --build= for the test's target, then =ctest -R=            |
| pytest    | the project's =.venv=, =venv= or =env= Python if it has one, else =python3= |
| unittest  | the same interpreter, with the standard library's =unittest=      |
| testthat  | =Rscript=. A package is loaded once with =pkgload::load_all= |

testthat's tests are found by reading the files, so a =test_that()= whose
description is computed (=paste("case", i)=) is not listed until a run reports
it. It then joins its file's group. Running one test runs just that block,
through =test_file(desc = ...)=, which needs testthat 3.2 or later. Running a
whole file runs it once.
| jest, vitest | the project's =node_modules/.bin= (or a parent's), else =npx=  |
| node:test | =node --test=                                                     |

mep runs each one through a small driver or reporter of its own, so it
reads results from the runner itself rather than from its console output.
pytest still reads the project's own configuration (=addopts= included).
When a runner is not installed, its tests are marked /could not start/.

#+begin_src lua
mep.opt.lang_test_python = 'unittest'      -- 'auto' (default), 'pytest', 'unittest'
mep.opt.activity_test_python_bin = '/opt/py/bin/python3'
mep.opt.activity_test_rscript = '/usr/local/bin/Rscript'
mep.opt.activity_test_node = 'node'
mep.opt.activity_test_scan_depth = 2
#+end_src

** ctest

The CMake build directory is the first entry of
=mep.opt.lang_test_build_dirs= that holds a configured ctest tree, looked
for at the project root and in any subdirectory with its own
=CMakeLists.txt=. The tree's =CTestTestfile.cmake= need not be at the top
of the build directory: a project that only calls =enable_testing()= in
=tests/CMakeLists.txt= gets one in =build/tests=, so mep looks up to three
levels down and lists each one it finds as its own suite
(=build/debug/test/cpp= and =build/debug/test/cpp-focused= are two). Set
=mep.activity_test_build_dir= to pick one yourself, and
=mep.opt.activity_test_jobs= to run tests in parallel:

#+begin_src lua
mep.activity_test_build_dir = 'build/native-dev'
mep.opt.activity_test_jobs = 8
#+end_src

Tests come from ordinary CMake: =enable_testing()= and one =add_test()=
per test. A test's group is its first label that not every test carries:
mep's own tests are all labelled =unit=, plus the area they cover (=cad=,
=pdf=, =mepml=, =lsp=, ...), so they group by area, and =ctest -L cad= runs
one area from the shell.

#+begin_src cmake
set_tests_properties(my-test PROPERTIES LABELS "unit;parser")
#+end_src

 Before running a test, mep builds the target its executable comes
from. For a target nobody has built yet, it builds the target named after the
test. mep's own windowless test binaries are registered this way, so
=ctest --test-dir build/native= runs the same suite.

** Adding a kind of suite

A provider is a Lua table that finds suites, lists their tests and says how
to run them. Register one from =init.lua= and it is searched for alongside
the built-in ones. One registered under an existing =id= replaces it, and
=enabled = false= turns one off:

#+begin_src lua
mep.test_provider_register({
  id = 'cargo', name = 'cargo',
  -- Called for each directory searched; entries maps name -> 'file' | 'dir'.
  detect = function(dir, entries, depth)
    if entries['Cargo.toml'] == 'file' then return {} end
  end,
  -- done({{name = ...}, ...}) or done(nil, 'why not').
  list = function(suite, done)
    done({{name = 'all'}})
  end,
  -- Optional: the test's group path and a shorter label for its row.
  -- 'crate::module::test' -> {'crate', 'module'}, 'test'.
  group = function(suite, test)
    return nil
  end,
  -- argv (run in the suite's directory) for `names`, nil meaning every test.
  command = function(suite, names)
    return {'cargo', 'test'}
  end,
  -- The run's output lines -> {{name, status, seconds, output}, ...}.
  -- Without it (and parse_line, for live marks) the protocol below is read.
  parse_output = function(lines)
    local ok = false
    for _, l in ipairs(lines) do
      if l:match('^test result: ok') then ok = true end
    end
    return {{name = 'all', status = ok and 'passed' or 'failed', seconds = 0, output = lines}}
  end,
})
#+end_src

The built-in drivers report one line per event, which the default parsers
read:

#+begin_example
@@mep-test case NAME
@@mep-test start NAME
@@mep-test result passed|failed|skipped SECONDS NAME
#+end_example

A result claims the output printed since the line before it. A runner that
can print these lines needs no parsers of its own: =mep.test_provider_list_job=
runs a listing command and collects its =case= lines. =mep.activity_test_suites()=
returns what the panel shows, for scripts and agents.

** No suites found

When nothing is found, or =mep.activity_test_cmd= is set,
=:MepActivityTestRun= runs one whole-suite command instead
(=mep.activity_test_cmd=, or =npm test= when there is a =package.json=)
and lists its failure lines. =mep.activity_test_failure_lines()= exposes
them to Lua.
